## 1. 架构：核心与框架彻底解耦

```
                    ┌──────────────── 核心层（零框架依赖）────────────────┐
  PDF ──► MinerU ──►│ 解析 → 两级分块 → 图片语义标注 → 三路向量 → Qdrant │
                    └────────────────────────┬───────────────────────────┘
                                             │
                                    ┌────────▼────────┐
                                    │  检索服务        │  混合检索 + RRF + rerank
                                    │  (stdlib HTTP)   │
                                    └────────┬────────┘
                                             │
                        ┌────────────────────┼────────────────────┐
                        ▼                    ▼                    ▼
                  adapters/dify       adapters/openwebui      你自己的前端
```

**核心层不知道 Dify 的存在。** 换框架只写新适配器，核心一行不改。

### 1.1 关键设计：核心模型不为框架妥协

Dify 的索引结构是「每 segment 一个文本向量 + 每附件一个图片向量」，
存不下融合向量，也不保存 bbox / 表格 HTML / 章节树。

**如果按 Dify 的能力设计模型，就等于把它的缺陷固化进核心。**
所以核心的 `Chunk` 完整保留所有信息，由适配器负责降级映射 ——
丢什么、怎么丢，是适配器的责任。

### 1.2 核心模型（`mmkb/models.py`）

| 模型 | 承载的信息 |
| --- | --- |
| `Block` | 类型 / 文本 / 层级 / bbox / 表格 HTML / 公式 LaTeX / 图片路径 / 图注 |
| `Section` | 标题路径 / 页码范围 / 块列表 / 分片序号 |
| `Chunk` | 正文 / 章节路径 / **图片对象列表** / 页码 / bbox / 顺序 / **三路向量** |
| `ImageRef` | 路径 / 图注 / 脚注 / bbox / 页码 / **VLM 语义描述** |
| `RetrievedChunk` | **框架无关**的检索返回结构（适配器负责翻译） |

## 2. 三路向量：Dify 做不到的事

一个 chunk 对应一个 Qdrant point，带三个**具名向量**：

| 向量 | 类型 | 维度 | 用途 | 实测价值 |
| --- | --- | --- | --- | --- |
| `fusion` | dense | 2560 | 正文 + 图 → **融合成一个向量** | 跨模态 Top-1 **95%** |
| `text` | dense | 1024 | 正文 + 图片描述（纯文本） | 不依赖跨模态对齐 |
| `image` | **multivector** (`max_sim`) | 2560 × N | 每张图各自成向量 | 以图搜图 |

检索：多路并行 → **RRF 融合**（只用排名，避免量纲不一致）→ **rerank 精排**。

> **踩坑**：Qdrant 的 multivector 必须写在**同一次** `PUT /collections/{name}`
> 的 `multivector_config` 里，单独调 `/vectors/{name}` 端点不生效。

### 3.6 Dify 端到端验证

已在 Dify 里**真实注册**外部知识库并跑通命中测试：

```
注册外部 API   → 201  (id d1d41701…)

命中测试       → 200
   score=0.9522  第18页  含 Markdown 图片语法
```

**关键发现：Dify 的 SSRF 防护会拦截本机/私有 IP 的检索服务**，
注册时报 `failed to connect to the endpoint`。需要在 `~/dify/docker/.env` 设：

```bash
SSRF_PROXY_ALLOW_PRIVATE_IPS=172.17.0.0/16   # Docker 网桥段
```

然后重启 `ssrf_proxy` 与 `api`。（这是 Dify 的安全设计，不是 bug；
但它也说明**对接自建服务有额外的适配摩擦**。）

## 4. 框架选型结论（详见报告 08）

### 4.1 最重要的认知纠正

> **痛点不是"框架渲染能力差"，而是"检索结果被当成了 LLM 的上下文，而不是 UI 的内容"。**

Dify / MaxKB / FastGPT 的链路是：

```
检索片段 → 塞进 prompt → 指望 LLM 把图片 markdown 复述出来 → 才能渲染
```

这条链路天然脆弱（模型可能删掉/改写/转义 URL）。
MaxKB 官方指南甚至教用户在提示词里补一句"对于已知信息中的图片，必须要在答案中进行输出"
—— 这恰好证明了问题所在。

**所以选型的唯一标准是：框架能不能让你把检索产物直接、确定性地写进 UI。**

### 4.2 推荐

| 角色 | 选择 | 理由 |
| --- | --- | --- |
| **首选** | **Open WebUI + Pipe Function** | 唯一同时满足「Markdown 图片必渲染 + 后端 Python 完全自定义 + 单容器轻量」 |
| 备选 | Chainlit | Apache-2.0 最干净；带 `rehype-raw`，**原始 `<img>` 也能渲染** |
| 备选 | assistant-ui + streamdown | 自写前端的渲染上限最高（专治流式中途未闭合的图片语法） |
| 不推荐 | 继续在 Dify 打补丁 | 契约里没有图片字段，图片靠 LLM 复述，同一个坑 |
| 不推荐 | RAGFlow / FastGPT / MaxKB | 检索层不可替换；RAGFlow 明确不支持图片作为检索模态 |

### 4.3 两个必须注意的坑（源码级结论）

1. **Open WebUI 只渲染 `![]()`，不渲染原始 `<img>`**
   （`HTMLToken.svelte` 只特判 video/audio/iframe/status/file，其余按纯文本输出）
   → 本平台的流水线**已统一输出 Markdown 图片语法**。

2. **Open WebUI 的 "External Knowledge" 连接只支持 qdrant/milvus/pgvector 直连向量库**，
   不是任意 HTTP 检索 API → 必须用 **Pipe Function**，不要指望它的外部知识库配置。

### 4.4 Open WebUI 真实渲染验证（已实测，不再是推断）

调研报告里"Open WebUI 能渲染 `![]()` 但不能渲染 `<img>`"原本只是**源码级推断**。
本轮用 Playwright + 无头 Chromium **实际打开 Open WebUI 发问并检查 DOM**：

```
指向我们检索服务的 <img>: 3
  [1] 加载成功=true  尺寸=470x292  可见=true
  [2] 加载成功=true  尺寸=618x406  可见=true
  [3] 加载成功=true  尺寸=709x426  可见=true
回答里出现 '![' 字面量（说明没渲染）: false
→ ✅ 图片确实渲染并加载成功
```

截图（`multimodal-kb/docs/evidence/openwebui_rendered.png`）里可以看到：
- **电路图正常显示**（单相三线制用电器接线图，含"相线/工作零线/PE/N/L/用电器"全部标注）
- **LaTeX 公式正常排版**：$I'_r = \frac{R_g}{R_r}I_r$ (1-2)
- **章节路径引用**：`[4] 电子工艺实训基础 > 1.5 用电安全技术 > 1.5.1 接地和接零保护（第 18 页）`

**这说明 `![]()` 的结论成立，且整条链路（检索 → 图片 URL → 浏览器渲染）是通的。**

### 4.5 本平台的两个适配器对比

| | Dify | Open WebUI |
| --- | --- | --- |
| 接入方式 | External Knowledge API | Pipe Function（Python, in-process） |
| 图片能否**确定性**展示 | ❌ 靠 LLM 复述 | ✅ **代码直接写进流** |
| 适配代码量 | ~70 行 | ~140 行 |

## 6. 与 Dify 的关系（明确）

- **Dify 不再是知识库的载体，只是一层适配器**
- 旧的 `电子工艺实训-结构化` 知识库（336 父块/431 子块，Dify 内）**保留作对比**
- Dify 里要做图片展示，只能靠提示词要求 LLM 复述 —— 这是它的架构限制，我们不为此改核心
- 迁移到 Open WebUI 只需要：把 `adapters/openwebui/pipe.py` 放进 `data/functions/`
