## 一、跨模态框架调研结论（回应"先找现成框架"）

> 完整报告：[06_融合多模态向量框架调研.md](06_融合多模态向量框架调研.md)

**核心结论：没有任何框架能开箱提供「正文+图 → 单个融合向量」** ——
因为**融合是模型侧能力，不是库能力**。向量库只负责"把这个向量存好、检回来"。

所以真正的问题不是"找框架"，而是两件事：
1. 换一个**能落融合向量 + 并存文本/图片向量 + 混合检索**的库
2. 把检索服务包装成 Dify 的**外部知识库**

### 1.1 能落融合向量的库（都现成）

| 框架 | 融合向量 | 多向量/MaxSim | 许可证 | 部署 |
| --- | --- | --- | --- | --- |
| **Qdrant** | ✅ | ✅ `max_sim`（v1.10+） | Apache-2.0 | **低（推荐）** |
| Milvus 2.6.x | ✅ | ✅ StructArray + EmbeddingList | Apache-2.0 | 中-高 |
| Weaviate | ✅ | ✅ multi-vector | BSD-3 | 中（Dify 内部就是它，但 schema 固定） |
| LanceDB | ✅ | ✅（仅 cosine） | Apache-2.0 | 极低 |
| Vespa / Elasticsearch | ✅ | ✅ ColBERT / `maxSimDotProduct` | Apache-2.0 / ELv2 | 中 |
| pgvector / Chroma | ✅ | ❌ 单向量 | — | 极低 |

### 1.2 与 Dify 的集成路径

**External Knowledge API**（契约极简，源码只校验 200 后透传）：

```
请求: { knowledge_id, query, retrieval_setting:{top_k, score_threshold}, metadata_condition }
响应: { "records": [ { "content", "score", "title", "metadata" } ] }
```

**⚠️ 关键限制：契约里没有图片字段。** 图片只能以 Markdown/URL 文本放在 `content` 里，
Dify 前端是否渲染成图 —— **未验证，是唯一需要动手确认的点**。

### 1.3 不推荐的路

| 方案 | 原因 |
| --- | --- |
| 换 Dify 向量库 / 自研 embedding 插件硬塞融合向量 | Dify 的 schema 由它自己决定（每 segment 一个文本向量、每附件一个图片向量），**不改源码落不下融合向量** |
| Marqo | 已转向电商搜索，无融合向量入口 |
| RAGFlow | 维护者明确（issue #8750）不支持图片作为检索模态，图片一律 OCR/VLM 转文本 |
| ColPali/ColQwen 页面图检索 | 思路先进（页面整图 → patch 向量 + MaxSim），但**需 GPU**，中文教材效果无公开基准 |

### 1.4 结论与建议

用户要求"先找现成框架，没有或不兼容再自建" —— **答案是中间态**：

- ❌ 没有"装完就有融合向量"的框架
- ✅ **存储与检索层完全现成（Qdrant）**
- ✅ **集成层有官方契约（External Knowledge API）**
- → 所谓"自建"其实是**一个约 300 行的薄服务**，不是从零造框架

**建议**：先落地方案 A（图片语义文本化，本轮已完成），
若检索质量仍不满意，再上方案 B（Qdrant + 融合向量 + 外部知识库）作为增强。
可参考现成骨架：[dify-external-knowledge-base-proxy](https://github.com/yhuan416/dify-external-knowledge-base-proxy)。

## 二、章节树兼容性设计（回应"PDF 只是实例"）

你提醒得对：**不能硬依赖标题约定**。设计上用三级降级，任何文档都能用：

```
① 编号推导    1.4 → 1.4.1 判定更深；1.3.2 下出现 "1." 判定为子项
     ↓ 不适用
② MinerU level  用解析器给的 level 字段
     ↓ 不适用
③ 单级兜底    所有标题视为同级，只保留"最近标题"作为上下文
```

**无结构文档**（title 少于 3 个）：自动切到滑动分组，path 为空，
**完整上下文由父块（整段）提供** —— 即你说的"退回单级但保留完整上下文"。

### 实测：三类"不友好"文档都能正常处理

| 文档类型 | 结构化判定 | 行为 |
| --- | --- | --- |
| 正常教材（381 个标题） | True | 4 级章节树，2级178 / 3级137 / 4级18 |
| 无标题文档 | **False** | 滑动分组，path 空，上下文靠父块 |
| 标题全平 | True | 单级路径（最近标题） |
| 编号混乱（`A.`/`三、`/无编号） | True | 不崩，取最近标题 |

### 一个真实的坑（已修复）

MinerU 会把**列表项也标成 title**（如 `1. 安全措施` / `2. 安全操作`），
与真正的小节标题（`1. 2. 2 防止触电`）混在一起。
若对单段编号直接取段数，`2. 安全操作` 会被判成 1 级并**清空整个标题栈**，
污染后续所有路径。

**修正规则**：单段编号（`N.`）几乎都是列表项 → 判为**与上一个标题同级**；
且不允许它顶掉"文档级根标题"。

修复效果：路径异常率 **1.5%（5/336）**，且这些路径仍带可用上下文。

## 三、已建成的流水线

```
PDF
 │
 ├─① MinerU 解析           （官方 API 40s/100页，或本地 CPU 62s/100页）
 │     └─► content_list_v2.json：块类型 + bbox + 图注 + 表格 HTML + 阅读顺序
 │
 ├─② structure.py          结构重建 + 两级分块
 │     ├─ 过滤页眉/页脚/页码/空块
 │     ├─ 图注补偿（图注被标题隔开时，把图移到图注位置）
 │     ├─ 解析标题编号 → 重建章节树（三级降级）
 │     ├─ 父块 = 小节；子块 = 段落/列表项/表格
 │     └─ 子块正文前缀 = 【章节路径】
 │
 ├─③ describe_images.py    图片语义标注
 │     └─ qwen3-vl-flash，强制输出：图类型/所有可见文字/数值参数/符号连接/图注/概括
 │
 └─④ ingest_dify.py        写入 Dify
       ├─ 载体文档（hierarchical_model + 受控分隔符）
       ├─ 父块：POST .../segment（带 attachment_ids 精确绑图）
       ├─ 子块：由 Dify 按同一分隔符自动切分
       └─ text-embedding-v4 向量化
```

### 3.3 最终效果对比（同一批问题，两个知识库）

同一个 LLM（`qwen3-vl-flash`）、同一套提示词，只换知识库：

| 问题 | 旧库（Dify 内置扁平切分） | **新库（MinerU + 两级分块）** |
| --- | --- | --- |
| 手工焊接的步骤是什么？ | ❌ **"资料中未提及"** | ✅ 完整答出五步焊接法及每一步 |
| 接地保护示意图说明了什么？ | ❌ **"资料中未提及"** | ✅ 正确解释接地保护原理 |
| 胸外按压的操作要领？ | ⚠️ 答出体位，其余称"未提及" | ✅ 完整答出体位 + 按压位置确定 |
| 设备通电前做哪三查？ | ❌ **"资料中未提及"** | ✅ 准确列出三条 |

**4 个问题里，旧库 3 个答"资料中未提及"，新库 4 个全部正确。**

> **一个值得注意的现象**：旧库的相似度分数反而**更高**（如"手工焊接"0.904 vs 新库 0.666），
> 但回答质量差得多。原因是旧库的块更大更泛，向量上"看起来像"却缺少具体内容。
> **这提醒：不能只看检索分数，必须看最终回答。**

### 3.4 一处已知冗余（已修复，待重跑）

父块正文里子块的【章节路径】前缀会重复出现（父块自身已有前缀）。
已修正为：拼父块时剥掉子块的重复前缀。下次重跑入库即生效。

## 四、踩到并解决的坑（部署参考）

| 坑 | 现象 | 解法 |
| --- | --- | --- |
| 载体文档必须是**文本** | 用图片建载体 → `word_count=None` → `assert` 失败 → 500 | 用 `.md` 建载体，并**等索引完成**再写 segment |
| `attachment_ids` 键必须存在 | 省略该键 → `KeyError` → 500 | 始终传 `attachment_ids: []` |
| `hierarchical_model` 需要完整 process rule | 缺 `subchunk_segmentation` → 自动切子块抛异常 → **段落被静默标记为 error/disabled** | 建载体时给全 `pre_processing_rules` + `segmentation` + `subchunk_segmentation` |
| 父子结构下 Dify 会**自动**切子块 | 与手动子块冲突、数量不符 | 改用**受控分隔符**：父块用 `<<<KBCHUNK>>>` 拼接，`subchunk_segmentation.separator` 用同一串 → Dify 切出的就是我们的子块 |
| 标题路径不能自成一段 | 路径与首个子块之间多一个分隔符 → 单子块父块被切成 2 | 路径作为**前缀**拼进正文，不参与分隔 |
| `text-embedding-v4` 批上限 | 一次传 >10 条 → HTTP 400 | 按 10 条分批 |
| MinerU CLI `--output` | 给目录 → `Is a directory` | 给**文件**路径 |
| MinerU 本地 server | 默认 `mode=disabled` | `mineru config set parse_server.local.mode managed` 后**重启 server** |
| 容器跑 MinerU | `multiprocessing` → `PermissionError` | **给足 `/dev/shm`**（Docker 默认 64MB 不够） |
