## 0. 执行摘要

| 结论 | 证据 |
| --- | --- |
| **MinerU 本地 CPU 完全可用，且比预期快得多** | 100 页 **~62 秒**、峰值内存 **6.0 GB**（i5-13500HX / 12 线程 / 无 GPU） |
| **MinerU 官方 API 更快** | 100 页 **40 秒**，免费额度 1000 页/天 |
| **MinerU 解析质量显著优于 Dify 内置** | 图注关联 49% → **81%**；新增标题层级、bbox、表格 HTML |

| **最终建议：图片语义文本化，把多模态问题降维成文本问题** | 见第 5 节 |

## 1. MinerU 实测：本地 vs 官方 API

### 1.1 环境

| 项 | 值 |
| --- | --- |
| CPU | Intel i5-13500HX，10 核 20 线程，**有 AVX2，无 AVX-512** |
| 内存 | 我这侧沙箱可见 15.5 GB；**你实际宿主 32 GB** |
| GPU | 无（VM，NVML 被屏蔽） |
| MinerU | 4.0.7，**依赖无 torch**（ONNX + llama.cpp） |

### 1.2 实测数据

| 方式 | 档位 | 100 页耗时 | 峰值内存 | 成本 |
| --- | --- | --- | --- | --- |
| **官方 API** | vlm | **40 秒** | — | 免费 1000 页/天优先额度 |
| **本地 CPU** | basic（ONNX） | **~62 秒** | **6.0 GB** | 0 |
| 本地 CPU | standard（VLM/llama.cpp） | 10 页 34 秒（100 页未测） | 未测准 | 0 |

**换算**：本地 basic 档约 **0.6 秒/页**。

> 这个结果**远好于调研预期**（调研基于社区个案估计 100 页 2.5–30 分钟）。
> 原因：basic 档用的是轻量 ONNX 模型（PP-DocLayoutV2 + PP-OCRv6 Tiny/Small + PP-FormulaNet-plus-M），
> 且这台 CPU 单核性能较强。

### 1.3 一个重要发现：basic 与 standard 输出**完全一致**

对同一段（第 11–20 页）分别跑两档：

| 档位 | 引擎 | 文件大小 | 行数 | 标题数 | 图片数 | 表格数 |
| --- | --- | --- | --- | --- | --- | --- |
| basic | ONNX CPU | 20195 | 348 | 37 | 12 | 0 |
| standard | **VLM (llama.cpp)** | 20091 | 348 | 37 | 12 | 0 |

日志确认 standard 档**确实调用了 VLM**（`Using llama-cpp-engine as the inference engine for VLM`，
`VLM Predict: 6/6`），但**两者输出 diff 为零**。

**原因**：这份 PDF 是**数字排版、带文字层**的电子版，不需要 OCR，版面也规整。

**实践含义**：
- 你现有的这类 PDF → **basic 档足够，且快一个数量级**
- 后你提到要导入的**元器件 PDF**（扫描版数据手册）→ 那时 VLM 档才会体现价值
- 建议：**默认 basic，对扫描件/复杂版面自动或手动切 standard**

### 1.4 部署注意点（踩过的坑）

| 坑 | 现象 | 解决 |
| --- | --- | --- |
| `/dev/shm` 不可写 | `multiprocessing.Lock()` → `PermissionError` | **容器必须给足 `/dev/shm`**（Docker 默认 64MB 不够） |
| `--output` 要文件不是目录 | `Error: [Errno 21] Is a directory` | 写 `--output ./out.md` |
| CLI 默认只等 60 秒 | 100 页时提示 "still in progress" 并退出 | `--wait 600`，或后台继续（`mineru show parse <id>` 查状态） |
| 本地 server 默认关闭 | `Local parse-server is disabled` | `mineru config set parse_server.local.mode managed` 后**重启 server** |
| pip 装在用户目录 | 改 `HOME` 后 `No module named pip` | 装依赖时不要覆盖 `HOME` |

### 2.3 关键问题被验证解决

之前 Dify 里**图注错配**的两个典型案例，MinerU 都正确处理：

```
第 16 页（按阅读顺序）：
  0. [image] ''                                  ← 无题图
  1. [image] '图 人工呼吸示意图 图1-4 胸外按压示意图'   ← 图注与图在同一块 ✅
  2. [title L2] 1.3 设备安全用电
  ...
第 19 页：
  1. [image] '图 接地保护示意图'        ✅
  3. [image] '图 重复接地'              ✅
  5. [image] '图 单相三线制用电器接线'   ✅
```

对比 Dify 现状（同一个第 16 页区域）：图挂在 seg#4 末尾、图注「图 1-1」在 seg#5 开头，**两者分离**。

### 2.4 一个补充说明

`title.level` 只区分出 1 和 2 两级（3 个 level-1 + 378 个 level-2），**层级偏浅**。
但标题文本**自带小节号**（`1.3 设备安全用电`、`1. 3.1 设备通电前检查`），
可以**自己解析编号重建三级章节树**。这比依赖 `level` 更可靠。

## 3. Embedding 实测：本次最关键的发现

### 3.1 实验设计

从 MinerU 抽出的图片里选出 20 组「**图 + 对应图注**」（有标准答案），对比不同模型的检索能力：

- **文→图**：用图注文本作 query，看能否命中对应的图
- **图→文**：用图作 query，看能否命中对应的图注

### 3.2 结果

| 模型 / 路线 | 维度 | 文→图 Top-1 | 平均排名 | 图→文 Top-1 |
| --- | --- | --- | --- | --- |
| `multimodal-embedding-v1`（**当前在用**） | 1024 | **40%** | 4.60 | 40% |
| `tongyi-embedding-vision-plus` | 1152 | **40%** | 2.75 | 40% |
| `qwen3-vl-embedding`（独立向量） | 2560 | **80%** | 1.40 | 75% |
| **`qwen3-vl-embedding`（融合向量）** | 2560 | **95%** | **1.05** | — |
| `qwen3-vl-rerank`（对全量重排） | — | **90%** | 1.15 | — |

> 随机基线：Top-1 = 5%，平均排名 10.5

### 3.3 三条结论

**① 当前模型确实很弱。** `multimodal-embedding-v1` 文→图 Top-1 只有 40%，
说明"图文融合向量空间"在实践中几乎没有对齐——这印证了主报告第 1 节的发现
（文本→图距离 0.885、排第 190/290）。

**② 同代换型无用，跨代才有效。** `tongyi-embedding-vision-plus` 依然是 40%，
而 `qwen3-vl-embedding` 跃升到 80%（独立）/ **95%（融合）**。

**③ 融合向量是最优解。** 把 text + image 放进**同一个 content 对象**，
输出**一个**向量 → 图文天然同位置，Top-1 达 95%、平均排名 1.05。

### 3.4 但融合向量在 Dify 里用不上

两个硬约束（详见 [03 文档第 1 节](03_方案验证与下一步测试计划.md)）：

1. **插件硬编码**：Dify 通义插件只对 `multimodal-embedding-v1` 走多模态接口，
   其余模型走 `TextEmbedding`。换模型必须自研插件。
2. **更根本**：Dify 的索引结构是「每 segment 一个文本向量 + 每 attachment 一个图片向量」，
   **没有地方存"某段正文 + 它的图"融合成的那一个向量**。

## 4. Rerank 是什么，要不要用

### 4.1 原理：两阶段检索

**Embedding 检索（双塔 / bi-encoder）**
```
query ──► [编码器A] ──► 向量 ┐
                            ├─► 余弦相似度
document ─► [编码器B] ──► 向量 ┘
```
- query 和 document **各自独立编码**，从不"见面"
- 优点：document 向量可**预先算好**，检索快（百万级毫秒响应）
- 缺点：只能比较**整体语义**，对细节差异不敏感
  （"焊接步骤" vs "焊接方法"，向量可能几乎一样）

**Rerank（交叉编码器 / cross-encoder）**
```
[query + document] ──► 一个模型 ──► 相关性分数
```
- query 和 document **拼在一起**送进模型，能看到词级交互
- 优点：**排序准确得多**
- 缺点：**无法预计算**，每个 (query, doc) 对都要跑一次 → 只能对少量候选做

**标准用法（两阶段）**
```
全部文档 (N = 10万)
   │ ① Embedding 检索（快，召回）
   ▼
候选集 (top 50)
   │ ② Rerank（准，精排）
   ▼
最终 top 5 → 交给 LLM
```

### 4.2 实测：rerank 确实有效

同样 20 组图文对，`qwen3-vl-rerank` 对全部 20 个候选重排：

| 方案 | 文→图 Top-1 | 平均排名 |
| --- | --- | --- |
| 当前 embedding 单独 | 40% | 4.60 |
| **rerank** | **90%** | **1.15** |
| qwen3-vl 融合向量 | 95% | 1.05 |

**rerank 把一个 40% 的弱检索拉到了 90%** —— 这就是它的价值：
**即使底层 embedding 一般，rerank 也能大幅补救。**

### 4.3 对你的场景为什么特别值得用

1. **我们的 chunk 会有大量相似内容**（同一本书相邻小节、相似的电路图描述），
   向量检索很容易混淆 —— rerank 正好治这个
2. **当前 embedding 区分度低**（实测 40%），rerank 的边际收益最大
3. **成本极低**：只对 top 20~50 个候选跑，不是全库
4. Dify 原生支持：知识库检索节点有 `reranking_enable` / `reranking_model`

### 4.4 在 Dify 里的可用选择

Dify 通义插件暴露的 rerank 模型：

| 模型 | 类型 |
| --- | --- |
| `qwen3-rerank` | 文本重排序 |
| `gte-rerank-v2` | 文本重排序 |

**没有多模态 rerank**（`qwen3-vl-rerank` 不在插件里）。

但这**不影响我们的方案** —— 因为按第 5 节的设计，图片语义会被转成文本，
所以**文本 rerank 就完全够用**。

> **建议**：先用 `qwen3-rerank`，在知识点检索节点里把 `reranking_enable` 打开，
> 用同一批问题对比"开/关 rerank"的效果。这是投入产出比最高的一步。

## 5. 最终方案

### 5.1 核心思路

**把"多模态检索"降维成"文本检索"** —— 因为：

- 融合向量（95%）在 Dify 里用不上
- 而图片语义一旦转成文本，就可以用**文本侧最强、最成熟的工具链**
  （强 embedding + rerank），不再受跨模态对齐的拖累

```
图片 ──(qwen3-vl-flash 详细描述)──► 语义文本
                                      │
              ┌───────────────────────┼───────────────────────┐
              ▼                       ▼                       ▼
          图注文本                VLM 详细描述            章节路径
              └───────────────────────┼───────────────────────┘
                                      ▼
                           写入子块正文（前缀）
                                      │
                    ┌─────────────────┴─────────────────┐
                    ▼                                   ▼
            文本向量（强文本模型）              图片作为 attachment
              → 图片语义可被检索                 → 随块返回给视觉 LLM
```

### 5.2 流水线

```
① MinerU 解析（basic 档，本地，~1 分钟/100 页）
     └─► content_list_v2.json：块类型 + bbox + 图注 + 表格 HTML + 阅读顺序

② 结构重建（自研）
     ├─ 解析标题编号（1.3 / 1.3.1）→ 重建三级章节树
     ├─ 按章节树切父块（最小一级小节）
     └─ 按语义单元切子块（段落 / 列表项 / 表格，不跨小节）

③ 图片锚定 + 语义标注（自研）
     ├─ 用 bbox + 阅读顺序把图绑定到所属子块
     └─ qwen3-vl-flash 生成详细描述（含图中文字、数值、符号）

④ 入库（Dify API，绕开自动切分）
     ├─ POST .../segment          → 父块（带 attachment_ids）
     ├─ POST .../segments/{id}/child_chunks → 子块（正文前缀含章节路径+图注+图片描述）
     └─ Dify 自动向量化
```

### 5.3 关键参数建议

| 项 | 建议 | 理由 |
| --- | --- | --- |
| 父块粒度 | **最小一级小节**（如 `1.4.1 防止机械损伤`） | 保证整节上下文完整、可检索 |
| 子块粒度 | **段落 / 列表项 / 单个表格** | 检索精度 |
| 子块正文前缀 | `【章节路径】+【图注】+【图片描述】` | 让子块自带上下文，且图片语义可检索 |
| Embedding | **改用强文本模型**（`text-embedding-v4` 或 `qwen3.7-text-embedding`） | 不再需要多模态，选检索最强的 |
| Rerank | **开启 `qwen3-rerank`** | 实测能把 40% 拉到 90% |
| 图片描述模型 | **`qwen3-vl-flash`** | 专用 VL，0.0005 元/千token，101 张图约 0.1 元 |
| 图片描述粒度 | **尽可能详细**（含图中文字/数值/符号） | 你要导入元器件 PDF，丝印、型号、参数都要保留 |

### 5.4 图片描述 prompt 设计要点

针对元器件数据手册场景，务必要求模型输出：
- 图的类型（电路图 / 示意图 / 曲线图 / 实物照片 / 表格截图 / 封装图）
- **图中出现的所有文字、型号、数值、单位**（这是元器件文档的核心信息）
- 图中的符号、连线关系、引脚标注
- 图注原文

> 这样即使后续要检索"某个型号的封装尺寸"，也能命中。

## 6. 一个可选的进阶方案（先不做，留作后手）

如果第 5 节的方案在检索质量上仍不满意，可以考虑**自建融合向量检索层 + 接入 Dify 外部知识库**：

Dify 支持 **External Knowledge API**（已验证）：
- `POST /console/api/datasets/external-knowledge-api` 注册我们的服务
- 检索时 Dify 调用 `ExternalDatasetService.fetch_external_knowledge_retrieval`
- **我们的服务只需返回 `{"records": [...]}`**

这样就能用上 95% 的融合向量，同时保留 Dify 的应用编排能力。

**代价**：需要自建检索服务 + 维护向量库。**建议先用第 5 节方案，不够再上这个。**
