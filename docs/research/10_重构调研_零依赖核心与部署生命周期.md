# 10 · 重构调研：零依赖核心、插件架构与部署生命周期

> 本报告回答"要不要重构、往哪重构"。结论基于 2025–2026 年的权威资料（PyPA 打包规范、ASGI 规范、
> 12factor、CPython 文档、Kubernetes 探针文档、Qdrant 文档）与仓库现状代码。
>
> **核心判断：部署故障不在核心逻辑，而在"生命周期/供给"这一层。**
> 这一层恰好是"零依赖"约束正在赔钱的地方；而核心库那一层，零依赖值得保留。

## 0. 一页结论

| 问题 | 结论 | 是否要引入第三方依赖 |
| --- | --- | --- |
| 1. 插件发现 | 用 `importlib.metadata.entry_points`（**它本身就是标准库**），路径加载只留作开发兜底。适配器拆成独立发行包，Docker 里统一装进同一个 venv。 | 否（发现机制零依赖） |
| 2. 配置 | 保留 `os.environ` + dataclass，但**必须补上 fail-fast 校验**。不要为核心引入 `pydantic-settings` / `dynaconf`。 | 否 |
| 3. HTTP 层 | **不要为了"换个框架"而换**。先修 stdlib 服务的具体缺陷；只有当你要对外提供 OpenAPI / 多消费者 API 时才上 FastAPI，且只让它跑 service 进程。 | 可选，仅 service 层 |
| 4. 生命周期 | 把 `ensure_schema()`（幂等建集合）放进**进程启动路径**，与 `kb init` 共用同一份实现。12factor 要求 admin 代码随应用一起发布，而不是被 shell 重写一遍。 | 否 |
| 5. 任务入口 | 保留 Make 作为薄的调度层（现在做对了）；真正的防漂移手段是**用测试锁住文档里的命令与健康契约**，不是换 `just`。 | 否 |
| 6. 向量库迁移 | 单集合不需要迁移框架。用 `SCHEMA_VERSION` + 集合内 schema 哨兵点的幂等 `ensure` 函数；不兼容变更=换集合名重建。 | 否 |

## 1. 插件/适配器架构

### 推荐

**核心保持零依赖，适配器用 entry points 发现，路径加载降级为开发期兜底。**

关键事实：`importlib.metadata.entry_points()` 属于**标准库**（3.10+ 支持 `group=` 选择器），
因此"用 entry points 做插件发现"与"核心零依赖"**根本不冲突**。当前项目用"按路径 `importlib` 动态加载"
换来的不是零依赖，而是一堆本可避免的脆弱性：

- 依赖 CWD / 相对路径，从 wheel 安装后失效；
- 没有版本号、没有冲突处理、没有优先级；
- 第三方无法 `pip install` 进来；
- 无法被 `kb doctor` 静态列举（只能运行时试）。

PyPA 明确给出三种官方发现方式（命名约定 / namespace 包 / 包元数据），并推荐包元数据即 entry points；
同时规定**消费者自定义的 group 名应以自有 PyPI 名开头 + `.`**——所以 group 用 `multimodal_kb.adapters`。

### 代码片段

```python
# multimodal_kb/adapters.py —— 核心包内，仍然零第三方依赖
from __future__ import annotations
import importlib.metadata as md
from typing import Protocol

GROUP = "multimodal_kb.adapters"

class Adapter(Protocol):
    name: str
    def register_routes(self) -> dict: ...

def discover() -> dict[str, "Adapter"]:
    found: dict[str, Adapter] = {}
    for ep in md.entry_points(group=GROUP):
        try:
            found[ep.name] = ep.load()
        except Exception as e:          # 插件坏了不能拖垮核心
            print(f"[adapters] 跳过 {ep.name}: {e}")
    return found

def load_by_path(path: str):            # 仅开发/调试用，文档里写明非稳定接口
    import importlib.util, pathlib
    p = pathlib.Path(path).resolve()
    spec = importlib.util.spec_from_file_location(f"_mmkb_ext_{p.stem}", p)
    mod = importlib.util.module_from_spec(spec); spec.loader.exec_module(mod)
    return mod
```

适配器发行包（`integrations/dify/pyproject.toml`）：

```toml
[project]
name = "multimodal-kb-dify"
dependencies = ["multimodal-kb==0.1.0", "httpx>=0.27"]

[project.entry-points."multimodal_kb.adapters"]
dify = "multimodal_kb_dify:ADAPTER"
```

### 打包进 Docker

多阶段构建里，核心与适配器**装进同一个 venv**，运行时镜像只拷 venv：

```dockerfile
RUN /opt/venv/bin/pip install --no-cache-dir . ./integrations/dify
```

注意 PyPA 规范已说明：**entry point 上挂 extras 的做法不再推荐**（那是 setuptools egg 时代的产物）。
可选依赖要声明在**适配器包自己的** `dependencies` 上，而不是 entry point 的 `[extra]`。
镜像里也应删掉 `/app/integrations` + `chmod -R a+rX` 这种"按路径兜底"的安排——
它正是 uid/权限问题的来源之一。装进 venv 后，适配器是普通已安装包，不存在源码目录读权限问题。

## 2. 配置管理：stdlib vs pydantic-settings / dynaconf / python-dotenv

### 推荐

**保留 `os.environ` + dataclass，但把它从"能跑"升级到"会拒绝启动"。**
零依赖约束在这一层值得保留——但理由不是"依赖不好"，而是**这个库的配置面很小且是 I/O 型**，
第三方库带来的收益（嵌套、多环境分层、Vault、CLI）本项目都用不到。

### 现状的真实缺陷（与"没上 pydantic"无关）

`_env_int` 静默吞掉 `ValueError` 并返回默认值：

```python
def _env_int(key, default):
    try:
        return int(os.environ.get(key, "") or default)
    except ValueError:
        return default          # ← MMKB_PORT=80a8 会静默变成 8088
```

`MMKB_PORT=80a8`、`MMKB_MAX_CHUNK_CHARS=""` 这类拼写错误会**静默降级**而不是报错。
这是独立于库选型的正确性 bug，换成 pydantic 只是"顺带被修好"。

### 各方案取舍（针对本项目）

| 方案 | 得到 | 代价 | 结论 |
| --- | --- | --- | --- |
| `os.environ` + dataclass | 0 依赖、可完全掌控 | 类型转换/校验要自己写 | ✅ 保留，补校验 |
| `python-dotenv` | `.env` 解析 | 仓库里已有 bash 版 `.env` 解析器（`kb` 脚本）→ **两个实现 = 漂移源** | ⚠️ 要么只在 service 入口用，要么删掉 bash 版 |
| `pydantic-settings` | 字段级报错、dotenv、secrets、嵌套、CLI | 拖入 `pydantic-core`（Rust 二进制 wheel）等 | ❌ 核心不要 |
| `dynaconf` | 多环境分层、Vault/Redis、文件格式 | **vendor 了 python-box/click/dotenv/ruamel-yaml/toml**，体量最大 | ❌ 明显过度设计 |

### 零依赖在 2026 年还值不值？

**分层看。**《Stdlib or Third-Party?》(arXiv 2605.21405) 对 44 个 stdlib-only 重实现做了基准：
- 约 **2/3 达到与参考库 2× 以内的性能**，部分还快 5–115×；
- 性能悬崖出现在 **C 扩展密集型**（图像、二进制序列化、底层加密），**不是**纯 Python 第三方库的固有开销；
- **配置加载类**（dotenv / config）被归为 simple 层，I/O 密集，与参考库"性能几乎持平"；
- 每个直接依赖平均放大 **8–10 个传递依赖**。

对本项目：核心做的是 urllib 请求 + JSON + 分块 + 字符串处理，全部落在"stdlib 够用"的区间。
**所以：核心库保留零依赖是理性的；把这个约束扩张到运维层（HTTP 框架、迁移工具、配置校验库）是非理性的。**

### Fail-fast 校验（建议实现）

```python
# multimodal_kb/config.py
class ConfigError(RuntimeError): ...

def _env_int(key: str, default: int) -> int:
    raw = os.environ.get(key)
    if raw is None or raw == "":
        return default
    try:
        return int(raw)
    except ValueError:
        raise ConfigError(f"{key}={raw!r} 不是整数（当前默认 {default}）") from None

@dataclass
class KBConfig:
    ...
    def validate(self, *, need_llm: bool = False) -> None:
        """收集全部问题一次性抛出——不要让用户改一个跑一次。"""
        errs, warns = [], []
        if not (1 <= self.service_port <= 65535):
            errs.append(f"MMKB_PORT={self.service_port} 不在 1..65535")
        if not self.qdrant_url.startswith(("http://", "https://")):
            errs.append(f"QDRANT_URL={self.qdrant_url!r} 必须以 http(s):// 开头")
        if self.mineru_mode not in ("api", "local"):
            errs.append(f"MINERU_MODE={self.mineru_mode!r} 只能是 api | local")
        if need_llm and not self.dashscope_api_key:
            errs.append("DASHSCOPE_API_KEY 未设置（检索/入库需要）")
        if self.mineru_mode == "api" and not self.mineru_token:
            warns.append("MINERU_MODE=api 但 MINERU_TOKEN 为空，入库会失败")
        if errs:
            raise ConfigError("配置有误：\n  - " + "\n  - ".join(errs + warns))
        for w in warns:
            print(f"⚠️  {w}")
```

**调用点**：进程启动边界（`cli.main()` 分发后、`serve()` 建 server 前），**不要**放在模块导入期。
按 12factor 的原则，配置是"每个 deploy 各自正交管理"的粒度化环境变量——当前 `KBConfig.from_env`
的设计其实已经符合，值得写进 ADR 保留。

## 3. 手写 `http.server` 要不要换掉？

### 推荐（有倾向性）

**不要以"换成 FastAPI"作为解决方案。** 部署故障的根因是**初始化逻辑放在了 shell 脚本里**，
换框架不会自动修好它。分两步走：

1. **现在**：修 stdlib 服务的 4 个具体缺陷（见下），把 init 挪进进程启动路径。这一步不引入任何依赖，
   保住"clone 下来就能跑"的卖点。
2. **触发条件满足时**再上 FastAPI：当你需要 **OpenAPI 文档**（给 Dify/Open WebUI 自动生成集成）、
   多消费者 API 版本化、或请求校验/中间件生态。**且只让 FastAPI 跑 service 进程，核心库保持框架无关。**

### stdlib 服务的真实缺陷（来自 CPython 官方文档）

- **官方定性**："`http.server` is not recommended for production. It only implements **basic security checks**."
- **CRLF 头注入**：`send_header()` / `send_response_only()` **不做输入校验**，不拒绝 CRLF。
  当前代码把用户输入放进 body 而非 header，是对的——但要作为**硬约束写进代码注释与测试**，
  否则某天有人把 `query` 塞进 `X-Query` 头就是一个头部注入。
- **keep-alive 默认关闭**：`protocol_version` 默认 `'HTTP/1.0'`。要启用持久连接必须显式设为 `HTTP/1.1`，
  且**每个响应都必须带准确的 `Content-Length`**。当前每请求一条 TCP 连接，Dify/httpx 侧多付 RTT。
- **线程模型无上限**：`ThreadingHTTPServer` 每连接一线程（`daemon_threads = True`），
  没有线程池上限、没有请求读超时、没有 body 大小上限（`_body()` 直接按 `Content-Length` 读满内存）。
  这是明确的 DoS 面。至少要加：body 上限、socket 超时、并发上限。
- **无优雅停机 / 无 TLS**（3.14 起才有 `HTTPSServer`；生产一律建议前置反代）。

### 换成 FastAPI 的得失

| 得到 | 说明 |
| --- | --- |
| OpenAPI schema | 直接消除 Dify/Open WebUI 集成的**手写客户端漂移**（现在靠 `integrations/**/*.py` + YAML 模板手工对齐） |
| 请求校验 | 现在 `int(p.get("top_k", 5))` 遇到 `top_k="abc"` 会 500；框架会给 422 + 字段级错误 |
| lifespan 钩子 | 见第 4 节——但**这一条你用 stdlib 也能做到** |
| `TestClient` | 测试不用真绑端口；现在 `tests/smoke_test.py` 需要服务在跑 |
| 异步并发 / 中间件 / 结构化错误 | 明确收益，但本服务 QPS 量级下非瓶颈 |

| 失去 | 说明 |
| --- | --- |
| 依赖体积 | `fastapi + starlette + pydantic + pydantic-core + uvicorn + h11 + click + typing-extensions + annotated-types`。**具体增长请实测**（构建后 `docker image ls` 对比），不要凭感觉 |
| "可被别的项目直接引用" | 核心库不受影响（框架无关），但 service 进程不再能零安装运行 |
| 冷启动 | uvicorn 导入开销通常在数百毫秒量级，对常驻容器不构成理由 |
| 掌控力 | 线程模型/执行模型被框架接管 |

## 4. 生命周期：startup/init 应该写在哪

### 推荐

**幂等的 `ensure_schema()` 只有一个实现，两个入口：`kb init`（12factor admin 进程）与进程启动钩子。**
**绝不允许第三个实现藏在 shell 脚本里。**

### 规范依据

- **ASGI Lifespan 协议**：服务器在收到 `lifespan.startup.complete` 之前**必须先不处理连接**；
  若应用发回 `lifespan.startup.failed`，**服务器应记录并退出**。
  这正是你想要的语义：**起不来就崩，而不是起来之后一直 503**。
- **FastAPI `lifespan`**：`@asynccontextmanager` + `yield`，`yield` 前做启动初始化。
- **12factor XII Admin processes**：迁移等管理任务作为**一次性进程**运行，且
  *"run in an identical environment as the regular long-running processes"*、
  *"the same codebase and config"*、*"**Admin code must ship with application code to avoid synchronization issues**"*。
  → 它要求的是"同一份代码/同一个 release"，**不是**"必须由人手动跑脚本"。
  所以"启动钩子 + CLI 命令共用同一函数"完全符合 12factor；而"shell 脚本里再写一遍建集合逻辑"违反它。

### 一个重要边界

- **单副本**（当前形态）：放进启动钩子最安全，直接消灭"忘了 init"这个失败模式。
- **多副本扩容后**：N 个副本并发建集合会竞争。Qdrant 建集合**不是事务**。
  届时应改为独立 Job / init container 先跑 `kb init`，副本用 `--skip-init` 启动；
  或用一个带 TTL 的分布式锁。
  现在就把接口留出来：`serve(..., ensure=True)`。

### 代码片段（当前 stdlib 服务，20 行达到同等语义）

```python
def serve(svc, host, port, ensure: bool = True):
    if ensure:
        try:
            svc.pipe.init_store()          # 幂等：存在即返回
        except Exception as e:             # 起不来就别接流量
            print(f"❌ 启动初始化失败：{e}", file=sys.stderr)
            raise SystemExit(2)
    httpd = ThreadingHTTPServer((host, port), make_handler(svc))
    ...
```

FastAPI 等价写法：

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    pipe.init_store()          # 幂等；抛异常 -> startup.failed -> uvicorn 退出
    yield
app = FastAPI(lifespan=lifespan)
```

### 顺带必须修的：探针语义

当前 `/health` 一次探测打 3 次 Qdrant（含一次 `exact` count），且被同时当作 liveness 与 readiness。
这是**把 liveness 和 readiness 混为一谈**——依赖不可用时会被反复重启（restart storm），
而不是被摘流量。按 Kubernetes 的定义拆成两个端点：

- `GET /healthz`（liveness）：**不碰任何外部依赖**，进程活着就 200。
- `GET /readyz`（readiness）：查 Qdrant 可达 + 集合存在 + 缓存 30s 的 count；
  未就绪返回 **503**，body 里给 `qdrant_reachable` / `collection_exists` / `points`。
- `deploy.sh` 轮询 `/readyz`（就绪语义），compose healthcheck 也指向它。

## 5. 任务入口与"文档/脚本漂移"

### 推荐

**保留 Make。** 当前 `Makefile` 的形态其实已经是对的：
- `help` 从 `## ` 注释生成 → **自文档化，不可能漂移**；
- 真正的逻辑在 `deploy/*.sh` 与 `kb` CLI 里，Make 只做薄调度 → **没有重复实现**。

换成 `just` / Taskfile 的收益是 DX（无需 `.PHONY`、真正的参数传递、内置 `.env` 加载、静态错误检查），
代价是给开发机和 CI 再加一个二进制。**在漂移问题被更高优先级的手段解决之前，不要为了审美换工具。**

> 如果你确实想换：`just` 的内置 `.env` 加载可以顺手删掉 `kb` 脚本里那 15 行手写 bash `.env` 解析器——
> 那个解析器是**第二个 `.env` 语义实现**，是真实的漂移源。这才是换 `just` 的正当理由。

### 防漂移的规则（这才是重点）

1. **文档不重述行为，只重述入口。** `README` / `docs/deployment.md` 里应写 `make deploy`，
   而不是把 `deploy.sh` 内部逻辑（"轮询 `/health` 等 200，40×3 秒"）抄一遍。
   本次漂移的根因正是：**行为改了（集合缺失返回 503），文档/契约没改。**
2. **把契约写成测试，而不是散文。** 新增 `tests/test_health_contract.py`：
   - 集合缺失 → `/readyz` 返回 503 且 `collection_exists == False`；
   - 集合存在 → 200 且 `status == "ok"`；
   - `/healthz` 在 Qdrant 不可达时**仍然 200**。
   这样 `deploy.sh` 的轮询逻辑、compose healthcheck、`docs/deployment.md` **三方都指向同一个测试**。
3. **可执行文档块测试。** 用 `pytest-codeblock` 或 `mdproof` 抽取 Markdown 里的 shell 代码块，
   在 CI 里跑只读的那些。最低成本版本：`make docs-check` —— 从 `README.md`/`docs/*.md` 抓出
   `kb <subcommand>`，与 `argparse` 的子命令表比对，捕获"文档里写了不存在的子命令"。
4. **命令表由 Make 生成。** 让 README 的"常用命令"小节由 `make help` 的输出生成，
   而不是手抄——手抄的表必然会漂。
5. **脚本本身进 CI。** 用一次性 compose project 跑 `deploy.sh --down` 与 `verify.sh`，断言退出码。
   `verify.sh` 现在对硬性失败返回非 0，这是对的，要保住。

## 6. 向量库 schema / 数据迁移

### 推荐

**不引入迁移框架。** 对"单集合、单写者、单实例"的项目，框架是过度设计；
但要把迁移的**纪律**（版本化、有序、幂等、留痕）用 60 行代码实现出来。

### 关键事实：Qdrant 的变更是两类，不是一类

- **兼容/可增量**：payload 索引、`hnsw_config`、`optimizers_config`、`quantization_config`、新增一个**具名向量**。
  → 幂等 `PUT`/`PATCH`，**可以安全放在启动钩子里**。
- **不兼容**：改 `size` / `distance` / `multivector_config.comparator`、重命名向量。
  → **必须新建集合并重新入库。这是数据迁移，不是 schema 迁移。**
  （这也是为什么 `create_collection(recreate=True)` 里那个 `DELETE` 必须被隔离在显式命令后面。）

### 幂等 `ensure_schema()` 模式

Qdrant 没有放"集合元数据"的地方，用**哨兵点**记录 schema 指纹：

```python
SCHEMA_VERSION = 3
SCHEMA_VECTOR = "__schema__"

def fingerprint(cfg) -> dict:
    return {
        "schema_version": SCHEMA_VERSION,
        "vectors": {"fusion": ("qwen3-vl-embedding", 2560),
                    "text":   ("text-embedding-v4", 1024),
                    "image":  ("qwen3-vl-embedding", 2560)},
    }

def ensure_schema(store, cfg) -> None:
    try:
        store.info()                        # 只捕获"不存在"，不要把网络错误也吞掉
    except CollectionNotFound:
        store.create_collection(...)
        store.upsert_sentinel(SCHEMA_VECTOR, fingerprint(cfg))
        return

    have = store.get_sentinel(SCHEMA_VECTOR)         # 可能为 None（旧集合）
    if have is None:
        raise SchemaMismatch(
            f"集合 {store.collection} 无 schema 记录（疑似旧版）。\n"
            f"  兼容做法： kb migrate --adopt\n"
            f"  重建做法： kb init --recreate  （会清空 {store.count()} 个点）")

    if have["vectors"] != fingerprint(cfg)["vectors"]:
        raise SchemaMismatch(
            "向量配置或 embedding 模型已变更，Qdrant 不支持原地改 size/distance。\n"
            f"  当前: {have['vectors']}\n  期望: {fingerprint(cfg)['vectors']}\n"
            "  请用新集合名重建： MMKB_COLLECTION=mmkb_v4 kb init && kb ingest --all")

    if have["schema_version"] < SCHEMA_VERSION:
        apply_compatible_steps(store, have["schema_version"])   # 只做增量步骤
        store.upsert_sentinel(SCHEMA_VECTOR, fingerprint(cfg))
```

**最关键的一条守卫**：指纹里必须包含 **embedding 模型名**，不能只有维度。
同维度换模型（或模型方静默升级）会产生**静默的错误召回**——这是比"维度不匹配报错"危险得多的事故。

### 要不要迁移框架

现有生态里确实有 `orthant`、`revector`（自称 "Alembic for vector collections"）这类工具。
**本项目现阶段不需要**。触发条件：多集合/多租户、多写者并发、或需要可回滚的审计级迁移。
在那之前，`alembic` 式框架给你的是"升级/降级脚本目录 + 版本表"，
而你只有一条 schema 演进线，收益 < 维护成本。

### 另外两个必须修的细节

- **`init_store()` 里的 `except Exception: pass`**：它把"集合不存在"与"Qdrant 500/超时"混为一谈，
  后者会盲目走 `create_collection` 然后报 409。必须区分 404 与 5xx/网络错误。
- **破坏性操作要显式 + 有回显**：`kb init --recreate` 应打印当前点数并要求确认，
  而不是一个参数就把集合删了。

## 7. 明确表态：零依赖约束在哪里赔钱、哪里值得留

### ✅ 值得保留

| 范围 | 理由 |
| --- | --- |
| `multimodal_kb` 库本体（parse/chunk/annotate/embed/store/search） | 全部 I/O 密集型；stdlib 在此区间与第三方库性能持平（zerodep 基准）。"换环境 / 进容器 / 被别的项目引用都不用装东西"是**真实且稀缺**的卖点。 |
| Qdrant REST via `urllib` | 这个量级上 `qdrant-client` 只带来 grpc/protobuf/numpy 级别的重量，没有收益。 |
| CLI via `argparse` | 足够，且 `kb` 脚本 + `pip install -e .` 双入口已经很好用。 |
| 测试 | 当前 `tests/` 用纯断言，无需 pytest 依赖，是优点。 |

### ❌ 正在赔钱

| 范围 | 代价 | 该怎么办 |
| --- | --- | --- |
| **手写 HTTP 服务作为"服务"** | 探针语义错、无请求校验、无 body/并发上限、无 keep-alive、adapter 路由自己重造。**这是零依赖约束伤害最大的地方。** | 先修 4 个缺陷 + 拆探针；需要 OpenAPI 时只给 service 进程上 FastAPI。 |
| **配置校验** | `_env_int` 静默降级这类 bug 是手写解析的直接产物。 | 补 `validate()`，仍然不引入库。 |
| **shell 里的初始化/迁移编排** | 与"零依赖"**毫无关系**——这纯粹是逻辑放错了层。 | 把它拉回 Python 的 `ensure_schema()`，shell 只调用。 |
| **`.env` 解析有两份实现**（`kb` bash 版 vs Python 侧） | 语义漂移（引号、注释、导出行为）。 | 二选一；换 `just` 可用其内置 dotenv 免费解决。 |
| **`/health` 混装 liveness + readiness** | 依赖抖动 → 容器反复重启。 | 拆 `/healthz` 与 `/readyz`。 |

### 一句话 ADR

> **"`multimodal_kb` 这个库零第三方运行时依赖"** 是一条好 ADR。
> **"本仓库所有进程都必须零依赖"** 不是——它把一个库的发布质量目标，错误地扩大成了整个系统的实现约束，
> 而本次部署故障恰好全部落在被这条扩张约束影响的那一层。
