# 融合多模态向量：知识库/检索框架调研

> 查询时间：**2026-09-26（UTC）**。Dify 最新版 **1.17.1**（2026-09-10 发布，GitHub Releases），与本地环境一致。
> 所有关键结论附来源链接；无法核实的一律标「未验证」，不做推测填充。

---

## 0. 结论速览

**① 「正文+图融合成一个向量」没有任何框架开箱即用 —— 因为它是模型侧能力，不是数据库能力。**
把 text 与 image 放进同一个 content 对象、由 `qwen3-vl-embedding` 设 `enable_fusion=true` 输出 **1 个** 向量，这是阿里云百炼官方文档明确定义的「多模态融合向量」模式（2560 维，支持中英日韩等 33 种语言，文本+图片/多图+文本/图+视频+文本）；
所有向量库只负责「把这个向量存好、检索好」。**所以不存在"装个框架就自动有融合向量"的选项；"换库/换框架能不能落这个向量、能不能混合检索"才是真问题。**

**② 「落融合向量 + 同时保留文本/图片向量 + 混合检索」完全现成。**
Qdrant（named vectors + multivector `max_sim`，v1.10+）、Milvus 2.6.x（StructArray + EmbeddingList + `MAX_SIM`，官方有 ColBERT/ColPali 教程）、Weaviate（named vectors + multi-vector + 多目标 join 策略）、LanceDB（multivector，仅 cosine）、Vespa（tensor 多向量 + ColBERT/ColPali 排序）、Elasticsearch（`maxSimDotProduct` 晚期交互打分）都能做。

**③ 与 Dify 的最佳路径就是 External Knowledge API**（用户已实测注册成功）：
官方契约只有 `{records:[{content, score, title, metadata}]}`（OpenAPI schema v1.3.1；官方中文文档明确 `content` = "检索到的文本分段，Dify 将其作为传递给 LLM 的上下文"）。
**契约里没有图片字段** —— 图片只能以「Markdown 图片链接 / metadata 里的 URL」文本形式返回；Dify 前端是否把它渲染成图，**未验证（需实测）**。

**④ RAGFlow 不是多模态向量方案，不能填这个缺口。**
仓库 91.3k★、Apache-2.0、非常活跃，但 issue #8750 中维护者/机器人明确答复：**"不支持把原始图片（或其 embedding）作为 chunk 内容检索；图片走 OCR，可选 VLM 生成描述，最终都以文本参与检索"**。它的 `/api/v1/retrieval` 可被包装成 Dify 外部知识库（已有社区代理项目），但检索仍是纯文本。

**⑤ ColPali/ColQwen 是另一条路线（晚期交互）**：页面整图 → 1024 个 patch × 128 维向量 + MaxSim，无需 OCR，能治表格/电路图/版面；代价是索引膨胀与 GPU。对你这套已实测 95% Top-1 的融合向量方案，它是**备选**。

**推荐路线（详见 §5）**：首选 = **External Knowledge API + 自建融合向量检索服务（Qdrant + qwen3-vl-embedding 融合向量 + BM25/RRF + qwen3-vl-rerank）**；备选 = Milvus `MAX_SIM` 多向量，或 ColQwen2.5 页面图检索试点；不推荐 = 换 Dify 向量库/插件硬塞融合向量、Marqo、RAGFlow 充当融合向量方案。

## 2. A. 原生多模态向量框架要点

- **Qdrant**：`max_sim` multivector 官方定义"变长同形稠密向量矩阵"，明确面向 ColBERT 类晚期交互；另有 named vectors 做「标题/摘要/正文多表征」。有 2026 年的 Turbo4 压缩多向量教程。**它不生成融合向量，但接受你生成的任何一个向量** → 你的场景最合适。
- **Milvus**：旧文档里的"多向量混合搜索"是**多字段 + WeightedRanker/RRFRanker**（查询期融合）；**2.6.x 新增 StructArray 的 EmbeddingList + `MAX_SIM`** 才是真晚期交互（支持 ColBERT/ColPali）。
- **Weaviate**：named vectors（每路独立 vectorizer/index/压缩）+ multi-vector（ColBERT 式，官方有 ColQwen2.5 + Qwen2.5 的 PDF 多模态 RAG 菜谱）+ 多目标检索 join 策略。**Dify 内部就用它，但 Dify 的 collection schema 固定为「文本向量/图片向量」两片，换库不换 schema 解决不了问题。**
- **LanceDB / Vespa / ES / pgvector / Chroma**：能存融合向量；Vespa、ES 有晚期交互打分；pgvector、Chroma 只有"一条记录一个向量"（多向量需多列/多次查询）。
- **Marqo**：star 5.0k、Apache-2.0、仍在维护（2.26.0，2026-04），但**产品已全面转向电商搜索与行为学习**；OSS 模型注册表里只有 CLIP（RN50/ViT-B/32…）与 sentence-transformers，**没有"融合向量"入口**；多字段是查询期 tensor 加权。不建议为此引入。
- **txtai**：Apache-2.0，多模态索引（图/文同空间）+ 图像描述 pipeline，但**融合单向量与多向量能力未验证**。

## 3. B. 晚期交互（ColPali/ColQwen）

- 原理与体积：页面图切 **32×32=1024 patch**，每 patch **128 维**，检索用 **MaxSim**。**本文计算**：fp16 ≈ 1024×128×2B ≈ **256 KB/页**（10 万页 ≈ 25 GB）；二值化到 1 bit/维 ≈ **16 KB/页**（10 万页 ≈ 1.6 GB），Qdrant/ES 都有二值化 + 重排实践。
- 生态：`illuin-tech/colpali`（colpali-engine，含 ViDoRe 榜单）、**Byaldi**（AnswerDotAI，851★，Apache-2.0，但最后提交 2025-01，偏停更）、`vidore/colqwen2.5-v0.2`（HF 模型卡标注 MIT，2026-08 更新）；存储侧 Qdrant / Milvus / Weaviate / LanceDB / ES / Vespa 均有官方教程。
- vs「图片语义文本化 + 文本检索」：ColPali 保留版面/表格/图表，抗 OCR 错误；劣势是**索引膨胀约 3 个数量级、必须 GPU、难以再做 BM25 关键词混合**。中文能力取决于底座 VLM（ColQwen2.5 基于 Qwen2.5-VL，理论多语；**中文教材实测未见公开基准，未验证**）。
- **冷启动成本警告**：这台机器目前是"无 NVIDIA GPU 也能跑 MinerU"的配置（见 04 报告），ColPali 索引 100 页教材在 CPU 上不可行/极慢（未验证具体下限），要先确认硬件。

## 4. C/D. 完整平台 与 Dify 集成路径

- **RAGFlow**：解析强（DeepDoc），但**检索是文本的**（§0④）；`POST /api/v1/retrieval` 参数齐全（含 `similarity_threshold`、`vector_similarity_weight`、`rerank_id`、`metadata_condition`），可被包装成 Dify 外部知识库；现成参考实现 `yhuan416/dify-external-knowledge-base-proxy`（33★，docker compose，专为对接 RAGFlow）。**FastGPT / AnythingLLM**：未发现融合向量或多向量能力（未验证），不作为方案。
- **LlamaIndex / LangChain**：`MultiModalVectorStoreIndex` 是"图像库 + 文本库分别建索引，查询时分别检索再合并"（分数/结果融合），**不是融合向量**；`MultiVectorRetriever`/`QueryFusionRetriever(RRF)` 同理。可当参考实现，不建议为此引入整框架。
- **Dify 集成四条路**（按推荐度）：
  1. **External Knowledge API**（首选）：在控制台注册外部知识库 API（用户已实测可用），Dify 请求 `{endpoint}/retrieval`，body = `knowledge_id/query/retrieval_setting{top_k,score_threshold}/metadata_condition`，你返回 `{"records":[…]}` 即可（源码 `external_knowledge_service.fetch_external_knowledge_retrieval` 只做 200 校验后透传 records）。**检索算法 100% 由你掌控**，Dify 侧零改动。
  2. Workflow HTTP 节点/自定义工具：可返回图片 URL，但要自己拼 prompt，失去"知识库引用"体验。
  3. 替换 Dify 向量库：官方支持 30+ 种（weaviate/qdrant/milvus/pgvector/elasticsearch/opensearch/chroma/tidb…，`VECTOR_STORE` 环境变量），**但 schema 由 Dify 决定，仍落不下融合向量**。
  4. 改 Dify 源码：成本最高、升级即冲突，仅在必须"引用面板里显示原图"时才考虑。

## 5. E. 自建最小可行实现 与 推荐路线

**MVP（约 1–2 天，300 行内）**：FastAPI 三端点（`/retrieval` 给 Dify、`/index` 入库、`/healthz`）+ Qdrant 单集合三路 named vector（`fusion` 融合向量、`text` BM25/sparse、`image` 图片向量）+ 入库时调 `qwen3-vl-embedding(enable_fusion=true)` 生成融合向量 + 检索时 dense/sparse 并行 → RRF → `qwen3-vl-rerank` 重排 → 按 Dify 契约返回 `content`（【章节路径】正文 + 图片 URL）、`score`、`metadata`。
关键工作量排序：① 入库流水线（解析产物 → 融合向量分组，最重）；② 混合检索与 RRF/rerank 调参；③ Qdrant 集合/索引与备份；④ Dify 外部知识库注册 + 图片在引用中的呈现（唯一需要实测确认的点）。

**推荐**：
- **首选**：Dify 保留为编排层 + 自建融合向量检索服务（Qdrant，或嵌入式先用 LanceDB），对外只暴露 `/retrieval`。现有 Dify 库可继续用（文本路线），融合向量库并行上线做 A/B。
- **备选**：Milvus 2.6.x `MAX_SIM`（若想同时上 ColBERT 式多向量）；或 ColQwen2.5 页面图检索小样本试点（先解决 GPU）。
- **不推荐**：换 Dify 内置向量库/自研 embedding 插件硬塞融合向量（schema 不改就是死路）；Marqo（电商导向、无融合入口、部署重）；RAGFlow 作为多模态解法（官方明确不支持）。
