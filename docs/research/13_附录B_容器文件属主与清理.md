# File Ownership for Containerized Services — Findings Brief

Scope: Docker Compose stack with a stateful Qdrant container (official image) writing to a bind mount
`../data/qdrant`, plus a Python API container that wrote `data/work/embed_cache.json` as root. Host CLI
(`kb ingest`) then hit `PermissionError`, and `rm -rf data/qdrant/*` partially deleted storage while a
cleanup script reported success.

All claims below were checked against primary sources (Docker/compose-spec/GNU/POSIX docs, the Qdrant
repo and CI, and linuxserver.io docs). Two claims in the original problem statement are inaccurate; they
are corrected in Q1 and Q6.

---

## TL;DR — recommended pattern

| Concern | Recommendation |
|---|---|
| Qdrant storage, no host access needed | **Named volume** (`qdrant_storage:/qdrant/storage`). Eliminates the whole ownership class. |
| Qdrant storage, host access needed (rsync/backup) | Bind mount **+ `qdrant/qdrant:<ver>-unprivileged` + `user: "${UID}:${GID}"`**. Never bind-mount a root-running Qdrant. |
| Python API container | `user: "${UID:-1000}:${GID:-1000}"` — never root. This alone fixes the `embed_cache.json` bug. |
| Cache/working dir touched by host CLI *and* container | Bind mount (a named volume cannot be reached by a host process without going through Docker), and make both sides the **same uid**. Do not use a named volume here: cross-device `os.replace()` fails with `EXDEV`. |
| PUID/PGID | Only meaningful for linuxserver.io images. Do **not** implement it in our own image, and it does nothing for Qdrant. |
| Cleanup of foreign-owned trees | Replace `[ -w dir ]` with a `find … ! -user` probe, and do the recursion as root *inside* a container. Check exit codes; never `\|\| true`. |
| Rootless Docker / userns-remap | Right systemic fix, wrong scope for this bugfix. Adopt as infrastructure work. `userns-remap` does **not** give you host-user ownership — skip it. |

## Q1 — The PUID/PGID pattern

### How it works
The container still starts as root. An init script (s6-overlay `init-adduser`) **renumbers the image's
existing unprivileged app user in place** to match the two env vars, then the supervisor drops to that
user to run the app:

```bash
# linuxserver/docker-baseimage-ubuntu — root/etc/s6-overlay/s6-rc.d/init-adduser/run
PUID=${PUID:-911}
PGID=${PGID:-911}
groupmod -o -g "${PGID}" abc
usermod  -o -u "${PUID}" abc
...
lsiown abc:abc /app /config /defaults      # note: NOT the mounted volumes
```

Consequences that matter for our bug:
- Files created inside volumes carry the host uid/gid → the host user owns them. This is exactly the
  problem we hit, solved at the source.
- It **does not** chown mounted volumes. Pre-existing wrongly-owned files still need a one-time
  `chown -R`. PUID/PGID prevents new damage; it does not repair old damage.
- Requires root at container init, so it is mutually exclusive with `--user` / `runAsNonRoot: true`.

### Pros / cons
Pros: one knob, no host-side `chown`, works for arbitrary host uids, no image rebuild, fixes both
"container can't write `/config`" and "host can't read files".
Cons: linuxserver.io–specific convention — no other image understands `PUID`/`PGID`; needs an init
process with root; `usermod -o` permits duplicate uids, which surprises some tooling; the app user has no
valid `$HOME` during init (`usermod -d /root` then restored); invisible to orchestrators.

### 2025–2026 status: not legacy, but scoped
linuxserver.io has **not** deprecated it. Their current docs still call it the method for their images and
state plainly: *"We are aware that recent versions of the Docker engine have introduced the `--user` flag.
Our images are not yet compatible with this, so we recommend continuing usage of PUID and PGID."*

They added a separate non-root mode (2024-12-17, revised 2025-08-13 and 2026-09-15) gated behind
`LSIO_NON_ROOT_USER`, and it is honest about the cost:
- `user:`/`--user` makes PUID/PGID inert: *"The PUID & PGID variables will not have any effect."*
- With `--user` you must manage all mounted-volume permissions yourself, Docker Mods don't run, custom
  services don't run, custom scripts are limited, and `no-new-privileges=true` requires `/run` to be
  owned by that user (they show a `tmpfs: - /run:uid=1000,gid=1000,exec` workaround).
- Support is *"on a Reasonable Endeavours basis and only for images which we have specifically tested."*
- For security they prefer rootless Docker over per-container non-root: *"generally, rather than starting
  containers as an unprivileged user, a better approach is to run Docker itself rootless, but that's not
  always practical."*

**Verdict:** PUID/PGID remains supported and recommended *by linuxserver.io for linuxserver.io images*.
It is a vendor convention, not a Docker feature, and it is not a pattern to adopt for our own image or to
expect from Qdrant. For our stack: set `user:` — it is one line and has none of the init-process baggage.

Sources:
- https://docs.linuxserver.io/general/understanding-puid-and-pgid/
- https://docs.linuxserver.io/misc/non-root/ (change history 2024-12-17 → 2026-09-15)
- https://github.com/linuxserver/docker-baseimage-ubuntu/blob/master/root/etc/s6-overlay/s6-rc.d/init-adduser/run
- https://github.com/orgs/linuxserver/discussions/5 (PUID/PGID vs `user`/`group_add`)

## Q2 — Compose `user:` vs image `USER` vs PUID/PGID entrypoint

### Precedence (authoritative)
compose-spec: *"`user` overrides the user used to run the container process. The default is set by the
image (i.e. Dockerfile `USER`). If it's not set, then `root`."*

```
docker run --user / compose user:   >   Dockerfile USER   >   root
```

| Mechanism | Where it lives | Changes with | Notes |
|---|---|---|---|
| Image `USER` | Dockerfile, baked per tag | Rebuild / new tag | qdrant's normal tags resolve to `USER 0:0` (see Q6) |
| Compose `user:` | compose file / `--user` | Every run, no rebuild | Cannot be changed after container create; also overrides `USER` for *everything* in the container, including init |
| PUID/PGID | Image's own entrypoint | Env vars | Only exists if the image implements it; needs root at init |

### Bind mounts: no uid translation in rootful Docker
The inode's numeric uid/gid on the host is what the container sees, verbatim. There is no mapping table
to configure. So:
- container process uid 0 → files created on the host are owned by host uid 0 (root) → this is bug #1;
- container process uid 1000 → files owned by host uid 1000 → host CLI works.

The only two knobs are (a) which uid the container process runs as, and (b) who owns the host directory.
Note also that an arbitrary `user:` uid usually has **no `/etc/passwd` entry** in the image, so `$HOME`
resolves to `/`, `whoami` fails, and any library that writes a cache under `$HOME` breaks. Prefer a uid
that exists in the image, or set `HOME` explicitly.

### Named volumes: ownership comes from the image, and is invisible to the host
On first use Docker copies the content of the image's target directory into the empty volume **with the
image's ownership**: *"If you mount an empty volume into a directory in the container in which files or
directories exist, these files or directories are propagated (copied) into the volume by default."* A
root-owned `/qdrant/storage` in the image therefore yields a root-owned volume — correct for the root
container, and the host user has no reason or ability to touch it. Volumes live under
`/var/lib/docker/volumes/<name>/_data`, which is root-only anyway, so the host user never hits
`PermissionError` by accident.

### Minimal YAML
```yaml
services:
  api:
    build: .
    user: "${UID:-1000}:${GID:-1000}"   # overrides Dockerfile USER; fixes embed_cache.json
    # group_add: ["2000"]               # only if a *shared group* must bridge two uids
    environment:
      HOME: /tmp                        # arbitrary uids often have no passwd entry
```

Sources:
- https://github.com/compose-spec/compose-spec/blob/main/spec.md (`## user`, `## group_add`, `## userns_mode`)
- https://docs.docker.com/engine/storage/volumes/ (pre-population, host-access caveat)
- https://docs.docker.com/engine/storage/bind-mounts/ ("Bind mounts have write access to files on the host by default")
- https://docs.docker.com/engine/security/userns-remap/

## Q3 — Bind mounts vs named volumes for stateful services

Docker's own decision rule is explicit: *"Volumes are not a good choice if you need to access the files
from the host, as the volume is completely managed by Docker. Use bind mounts if you need to access files
or directories from both containers and the host."* And for bind mounts: *"Bind mounts have write access
to files on the host by default… it may affect non-Docker processes on the host system."*

| | Bind mount | Named volume |
|---|---|---|
| Ownership conflicts with host | **Yes** — host inode uid/gid is used verbatim | **No** — Docker-managed, ownership from image |
| Direct host access (`kb ingest`, rsync, `rm -rf`) | Trivial | Requires a helper container (`docker run --rm -v vol:/v alpine …`) or `docker compose cp` |
| Lifecycle | Independent of Docker; survives everything | `docker volume rm`, removed by `compose down -v` |
| Portability across hosts | Breaks if the path/uid differs | Docker-managed, portable |
| Backup | Host tooling | `docker volume` / volume drivers / helper container |
| Deployment risk | Symlinks/`..` in the host path can widen what a container can write | None of that class |

### (a) Vector DB storage (Qdrant) → **named volume by default**
Qdrant only needs block-level POSIX storage, and its docs explicitly rule out the alternatives: *"Qdrant
won't work with Network file systems such as NFS, or Object storage systems such as S3."* Also: *"Using
Docker/WSL on Windows with mounts is known to have file system problems causing data loss."*
So: a plain **local** named volume. Do not back it with an NFS volume driver, and prefer a named volume
on Windows/WSL. This removes the root-owned-bind-mount problem entirely, because nobody on the host needs
to touch the files.

Qdrant's own docs use a bind mount for the Docker dev path (`- ./qdrant_data:/qdrant/storage`) — that is
only safe if the container is not root, i.e. the unprivileged image (Q6). If you want host access for
backups, **bind mount + unprivileged image + matching `user:`** is the supported combination.

### (b) Cache/working dir both host CLI and container must write → **bind mount, one uid**
A named volume is the wrong tool: only processes inside Docker can reach it, so the host CLI would have to
invoke a container for every cache read/write. Worse, `os.replace(tmp, cache)` for an atomic cache write
requires source and destination on the same filesystem; a named volume is a different filesystem from the
project tree, so the rename fails with `EXDEV`. Keep it a bind mount and make both sides the same uid
(`user: "${UID}:${GID}"` on the API container). If the container genuinely must run as root, the cache has
to move to a named volume *and* the CLI must go through a container — a bad trade.

If two *different* uids must share a directory, use a shared group + setgid rather than permissive modes:
```bash
sudo chgrp -R kbdata data/work
sudo chmod -R 2775 data/work        # setgid keeps the group on new files
```
```yaml
group_add: ["2000"]
```

Sources:
- https://docs.docker.com/engine/storage/volumes/ ("When to use volumes")
- https://docs.docker.com/engine/storage/bind-mounts/ ("When to use bind mounts", "Considerations and constraints")
- https://qdrant.tech/documentation/installation/ (storage requirements; Docker Compose example)
- https://github.com/compose-spec/compose-spec/blob/main/spec.md (`group_add` rationale: "multiple containers… shared volume")

## Q4 — Detecting and cleaning a tree with foreign-owned files (sudo-less docker)

### Why `[ -w dir ]` is the wrong test
Bash `-w file` is documented as *"True if file exists and is writable."* It is a single `access(2)` /
`faccessat(2)` check on **that one directory inode**. It says nothing about the ownership or permission
of the entries *inside* the tree you are about to recurse into. `data/qdrant` is the host-owned
mountpoint, so `[ -w data/qdrant ]` is true even when every child is `drwx------ root`. It is also
trivially true for root regardless of mode bits. Testing the root of a tree you are going to walk
recursively is a category error.

### Why `rm -rf` partially succeeds and returns nonzero
POSIX `unlink()` fails with `[EACCES]` when *"write permission is denied on the directory containing the
directory entry to be removed."* Removal requires write+search on the **parent directory**, not ownership
of the file. So `rm -rf` can delete entries in directories it can write (the host-owned mountpoint and its
host-owned children), descends into root-owned subdirectories, and fails on each entry there; it then
cannot `rmdir` those subdirectories because they are non-empty. `rm` deliberately does not abort at the
first error — it processes operand by operand — so you get a *partially* deleted tree with survivors.

Exit status is well specified: POSIX `rm` returns `0` only if *"each directory entry was successfully
removed"*, otherwise `>0` = *"An error occurred"*; GNU adds *"An exit status of zero indicates success, and
a nonzero value indicates failure."* So `rm -rf` **did** report the failure with exit code 1. The buggy
script destroyed the signal — `-f` only suppresses "no such file" and the write-protected prompt; it does
not turn errors into success. `2>/dev/null`, `|| true`, or simply not checking `$?` is what produced the
false success report.

### Reproduced locally (host-owned dir + one non-writable subdir — same failure shape as root-owned dirs)
```
$ [ -w dir ] && echo writable        → writable          (misleading)
$ rm -rf dir/*; echo $?              → 1
survivors: ro/  ro/inside.txt        (only the writable file was deleted)
$ rm -rf dir/* 2>/dev/null; echo $?  → 1                 (silent nonzero = the bug)
```

### Correct probe (ownership + writability, not `-w` on the root)
```bash
uid=$(id -u)
foreign=$(find "$dir" -xdev \( ! -user "$uid" -o \( -type d ! -writable \) \) -print -quit 2>/dev/null)
if [ -n "$foreign" ]; then
    echo "NOT purgable as $(id -un); first offender: $foreign" >&2
fi
```
`-user uname` (*"File is owned by user uname (numeric user ID allowed)"*) is the ownership test; the extra
`-type d ! -writable` catches directories we own but cannot write into. `-xdev` prevents walking off the
intended filesystem. `-print -quit` makes it a cheap boolean instead of a full walk.

### Correct cleanup with sudo-less docker
Root in a container has `CAP_DAC_OVERRIDE` in the container's user namespace, which under rootful Docker
maps to real host root — so it can unlink entries the host user cannot. Mount the **parent** and delete
the child (never mount the directory you are deleting), and verify afterwards:
```bash
set -euo pipefail
dir=../data/qdrant

# 1. Recursion as root inside a container.
docker run --rm -v "$(cd .. && pwd)/data:/data" alpine:3.20 \
    sh -c 'rm -rf /data/qdrant'

# 2. Verify — do not assume.
if [ -e "$dir" ] && [ -n "$(find "$dir" -mindepth 1 -print -quit 2>/dev/null)" ]; then
    echo "cleanup FAILED: $dir still has entries" >&2
    exit 1
fi
mkdir -p "$dir"
```
Do **not** use `rm -rf "$dir"/*`: with `nullglob` off an empty directory leaves the literal glob (an
error), and dotfiles such as `.qdrant-initialized` are missed. Do not use `find … -delete` as a host-side
fix — it is subject to exactly the same permission rules.

If docker is unavailable, the only honest behaviour is to detect and refuse:
```bash
find "$dir" -xdev ! -user "$(id -u)" -print -quit | grep -q . \
  && { echo "contains files not owned by $(id -un); run: docker run --rm -v ...:/data alpine rm -rf /data/qdrant" >&2; exit 1; }
```
`chmod -R` from the host does not help either (chmod on a root-owned inode requires ownership), and
`chown` requires `CAP_CHOWN`. Only root-in-container or real root can repair ownership.

Sources:
- https://pubs.opengroup.org/onlinepubs/9699919799/functions/unlink.html (`[EACCES]` on the containing directory)
- https://pubs.opengroup.org/onlinepubs/9699919799/utilities/rm.html (EXIT STATUS; `rm -r .*` warning)
- https://www.gnu.org/software/coreutils/manual/html_node/rm-invocation.html ("nonzero value indicates failure")
- https://man7.org/linux/man-pages/man1/find.1.html (`-user`, `-writable`, `-uid`)
- https://www.gnu.org/software/bash/manual/html_node/Bash-Conditional-Expressions.html (`-w file`)

## Q5 — Rootless Docker and `userns-remap`

### They solve different things, and only one of them helps us
Because the rootful daemon runs as root, container-uid 0 *is* host-uid 0. Rootless Docker changes that
mapping; the docs are explicit:

- **Rootless mode:** *"container UID `0` is mapped to the host UID of the user running rootless Docker
  (the result of `id -u`); container UID `n` (for `n >= 1`) is mapped to `subuid + (n - 1)`."* Then:
  *"This difference matters when setting file permissions on bind-mounted directories: in rootless mode,
  files owned by your host user appear as owned by `root` inside the container."* → **This does fix our
  bug class**: root-in-container files land owned by *us* on the host.
- **`userns-remap`:** maps container 0 to a high subuid (e.g. 231072). Files become owned by 231072, not
  by us. The docs concede the consequence: *"if volumes are mounted from the host, file ownership must be
  pre-arranged if you need read or write access to the volume contents."* → **This does not fix our bug**;
  it just changes which uid you have to fight. It also requires a fresh install: *"Enabling `userns-remap`
  effectively masks existing image and container layers… It is best to enable this feature on a new Docker
  installation rather than an existing one."*

### Current limitations (2026)
Rootless (https://docs.docker.com/engine/security/rootless/):
- Storage drivers: only `overlay2` (kernel ≥ 5.11), `fuse-overlayfs`, `btrfs`, or `vfs`.
- cgroup only with cgroup v2 + systemd; resource limits need extra setup.
- **Not supported:** AppArmor, checkpoint, overlay network, exposing SCTP ports.
- Privileged ports (<1024) need a workaround; `--cap-add` grants capabilities only within the container's
  user namespace, so operations needing capabilities in the *initial* namespace still fail.
- NFS as data-root unsupported; `docker run -p` does not propagate source IPs by default; `IPAddress` in
  `docker inspect` is namespaced.
- Setup prerequisites: `newuidmap`/`newgidmap` (`uidmap` package), ≥65536 subuids/subgids, and on Ubuntu
  24.04+ an AppArmor profile for `rootlesskit` (unprivileged user namespaces are restricted by default).
- The daemon socket moves to `$XDG_RUNTIME_DIR/docker.sock` (`DOCKER_HOST=unix:///run/user/1000/docker.sock`),
  which breaks any tooling that assumes `/var/run/docker.sock`.

`userns-remap` (https://docs.docker.com/engine/security/userns-remap/):
- Incompatible with `--pid=host` / `--network=host`; with `--privileged` unless `--userns=host`; and with
  external volume/storage drivers that don't understand the mapping.
- `mknod` is denied for the namespaced root.
- Remapped filesystems confuse programs that check ownership (e.g. `sudo`, setuid binaries).

### Practicality for a project depending on third-party images that assume root
Rootless works fine for Qdrant itself — it needs overlay2 (kernel ≥ 5.11), a local data-root, and no
privileged ports. Nothing in Qdrant needs real root; the "assumes root" assumption is only about *file
ownership of its data dir*, which rootless neutralises. But two frictions are real for us:
1. rootless is a **host-wide change** with a moved socket — every Makefile, script, and Python
   `docker.from_env()` that assumes `/var/run/docker.sock` needs `DOCKER_HOST` plumbed through;
2. ACL + rootless + named-volume-root edge cases are still rough upstream (docker/compose#13303,
   "Rootless Docker Volume Permissions Issue with User Namespace Remapping and ACLs", opened 2025-10-20,
   since closed).

LSIO's own recommendation for the security question is *"rather than starting containers as an
unprivileged user, a better approach is to run Docker itself rootless."*

**Verdict.** Recommended order:
1. **Now:** fix the uid at the Compose level (`user:` + the Qdrant unprivileged tag). Cheap, local, no host
   changes, and it fixes both reported bugs.
2. **Separately:** treat rootless Docker as an infrastructure decision with its own migration (socket path,
   cgroup v2, AppArmor profile, storage driver). Do not bundle it into a bugfix.
3. **Skip `userns-remap`** for this stack: it does not give host-user ownership, so it does not solve the
   problem, and it requires a fresh Docker install.

## Q6 — Can the official `qdrant/qdrant` image run as a non-root user?

**Yes.** The regular tags run as root by design, but Qdrant publishes dedicated unprivileged tags built
from the same Dockerfile. The claim "the official Qdrant image cannot run as non-root" is wrong.

### Evidence
1. **Dockerfile** — non-root is a first-class build option:
   ```dockerfile
   ARG USER_ID=0
   RUN if [ "$USER_ID" != 0 ]; then \
           groupadd --gid "$USER_ID" qdrant; \
           useradd --uid "$USER_ID" --gid "$USER_ID" -m qdrant; \
           mkdir -p "$APP"/storage "$APP"/snapshots; \
           chown -R "$USER_ID:$USER_ID" "$APP"; \
       fi
   ...
   WORKDIR "$APP"
   USER "$USER_ID:$USER_ID"
   ```
   With the default `USER_ID=0` this resolves to `USER 0:0` — i.e. the normal tags are explicitly root.
2. **CI publishes the variant**: `docker buildx build --build-arg='USER_ID=1000' …` tagged
   `qdrant/qdrant:<ver>-unprivileged`, `latest-unprivileged`, `<major>-unprivileged`,
   `<major.minor>-unprivileged`, cosign-signed like the rest.
3. **Tags exist and are current**: 74 `-unprivileged` tags on Docker Hub, back to at least `v1.13.4-unprivileged`
   (2025-02-17) through `v1.19.1-unprivileged`. So this is not a new or experimental affordance.
4. **Maintainer guidance** (qdrant/qdrant#6992, "Permission denied errors when copying QDrant storage files
   after docker container shutdown"), from `generall`: *"this problem is not related to qdrant, but rather
   to the docker… You can fix it by running `unprivileged` version of qdrant docker with propagated user,
   like this: `docker run --rm -it --network=host -v $(pwd)/qdrant-storage:/qdrant/storage -u $(id -u):$(id -g) qdrant/qdrant:v1.15.1-unprivileged`"*.
   `timvisee` confirms: *"No, nothing did change. The regular Qdrant image has always been using the root user."*
   The reporter confirmed it fixed their workflow.
5. **Kubernetes precedent** — qdrant-helm defaults to non-root and uses a two-step pattern:
   ```yaml
   containerSecurityContext: {runAsNonRoot: true, runAsUser: 1000, runAsGroup: 2000, ...}
   podSecurityContext:       {fsGroup: 3000, fsGroupChangePolicy: Always}
   image: {repository: docker.io/qdrant/qdrant, useUnprivilegedImage: false}
   updateVolumeFsOwnership: true
   ```
   with an initContainer
   `chown -R 1000:3000 /qdrant/storage /qdrant/snapshots`, gated on
   `updateVolumeFsOwnership && not image.useUnprivilegedImage`.
   The main container image reference appends `-unprivileged` when `useUnprivilegedImage: true`.
6. **Third party**: Chainguard ships a non-root-by-default Qdrant image, confirming there is nothing in
   Qdrant that requires root.

### What people actually do
- **Option A (recommended here):** use the `-unprivileged` tag and propagate the host uid:
  ```yaml
  services:
    qdrant:
      image: qdrant/qdrant:v1.19.1-unprivileged
      user: "${UID:-1000}:${GID:-1000}"
      volumes:
        - ../data/qdrant:/qdrant/storage
  ```
  Requires the host directory to be owned by that uid (`mkdir -p ../data/qdrant` as the host user is
  enough). Files created are then owned by the host user — `rm -rf` and `kb ingest` just work.
- **Option B:** keep the root image, run a one-shot root container that chowns, then run the app as
  non-root (this is literally what the Helm chart does with its initContainer). Do this only if you must
  stay on a root tag.
- **Option C (minimum change, no ownership coupling at all):** keep the root image and put
  `/qdrant/storage` on a **named volume**. Restores first-run ownership from the image, the host never
  touches it, and the bug disappears. Loses host-side `rm -rf`/rsync convenience.

### Why `user:` alone fails on the *regular* tag
`/qdrant`, `/qdrant/storage` and `/qdrant/snapshots` are root-owned in the root image, and the unprivileged
build is what creates the `qdrant` user and `chown -R`s `/qdrant`. Additionally Qdrant writes a startup
marker at a **cwd-relative** path, from `src/startup.rs`:
```rust
const DEFAULT_INITIALIZED_FILE: &str = ".qdrant-initialized";
fn get_init_file_path() -> PathBuf {
    std::env::var("QDRANT_INIT_FILE_PATH")
        .map(PathBuf::from)
        .unwrap_or_else(|_| DEFAULT_INITIALIZED_FILE.into())
}
```
With `WORKDIR /qdrant`, a non-root process cannot write `/qdrant/.qdrant-initialized` (the failure is only
logged as a warning — *"Failed to create init file indicator"* — but it breaks the OOM/recovery-mode path
in `tools/entrypoint.sh`, which keys off exit code 137 plus the marker's existence). The Helm chart
confirms this is a known constraint: it mounts an `emptyDir` at `/qdrant/init` and sets
`QDRANT_INIT_FILE_PATH=/qdrant/init/.qdrant-initialized`. If you must run the root tag as non-root, set
that env var and mount a writable path there.

## Concrete fix for this stack

### `docker-compose.yml`
```yaml
services:
  qdrant:
    # Unprivileged variant: USER 1000:1000, /qdrant chowned at build time.
    image: qdrant/qdrant:v1.19.1-unprivileged
    user: "${UID:-1000}:${GID:-1000}"
    volumes:
      - ../data/qdrant:/qdrant/storage     # owned by the host user
    ports: ["6333:6333", "6334:6334"]
    restart: unless-stopped

  api:
    build: .
    user: "${UID:-1000}:${GID:-1000}"      # fixes embed_cache.json ownership
    environment:
      HOME: /tmp                            # arbitrary uids usually have no passwd entry
    volumes:
      - ../data:/app/data                   # shared work dir; same uid on both sides
    depends_on: [qdrant]
```
One-time: `mkdir -p ../data/qdrant ../data/work` **as the host user** (do not pre-create with sudo).

If the root Qdrant tag must be kept, swap `volumes:` for a named volume and drop `user:`:
```yaml
    volumes:
      - qdrant_storage:/qdrant/storage
volumes:
  qdrant_storage:
```

### Cleanup script (replaces the `[ -w ]` + `rm -rf` script)
```bash
#!/usr/bin/env bash
set -euo pipefail

data_dir=$(cd "$(dirname "$0")/.." && pwd)/data
target="$data_dir/qdrant"
uid=$(id -u)

[ -d "$target" ] || { echo "nothing to clean"; exit 0; }

# 1. Probe by ownership/writability, never with [ -w ] on the root.
if find "$target" -xdev \( ! -user "$uid" -o \( -type d ! -writable \) \) -print -quit 2>/dev/null | grep -q .; then
    echo "==> storage contains entries not writable by $(id -un); purging via container"
    # 2. Root inside the container; mount the PARENT, delete the child.
    docker run --rm -v "$data_dir:/data" alpine:3.20 sh -c 'rm -rf /data/qdrant'
else
    rm -rf -- "$target"
fi

# 3. Verify; never report success on trust.
mkdir -p "$target"
if [ -n "$(find "$target" -mindepth 1 -print -quit 2>/dev/null)" ]; then
    echo "cleanup FAILED: $target is not empty" >&2
    exit 1
fi
echo "cleanup OK: $target is empty and owned by $(id -un)"
```

Rules encoded here: never `[ -w "$dir" ]`; never `dir/*`; never `2>/dev/null` or `|| true` on the delete;
always re-verify with `find`; always run `set -euo pipefail`.

## Corrections to the original problem statement

1. *"The official Qdrant image reportedly cannot run as non-root."* — **Incorrect.** Upstream publishes
   `-unprivileged` tags (`USER_ID=1000`) and Qdrant's maintainers recommend them. See Q6.
2. *"`rm -rf` … falsely reported success."* — `rm -rf` returned **exit 1**; it was the script that
   discarded the exit status (`-f`, stderr redirection, or no `$?` check). Partial deletion plus a nonzero
   exit is `rm`'s documented, POSIX-specified behaviour, not a silent success. See Q4.
