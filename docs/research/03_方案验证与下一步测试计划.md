## 一、Embedding 选型：一个重要修正

### 1.1 阿里云侧的多模态 embedding 分两条路线

查证 [百炼向量与重排序文档](https://help.aliyun.com/zh/model-studio/embedding-rerank-model)，
多模态 embedding 并非只有一种，而是**融合向量**与**独立向量**两条路线：

| 模型 | 向量维度 | 最大Token | 路线 | 官方定位 |
| --- | --- | --- | --- | --- |
| `qwen3-vl-embedding` | 256~2560（默认2560） | 32,000 | **融合 + 独立** | 图文混合检索 |
| `qwen2.5-vl-embedding` | 512~2048 | 32,000 | 仅融合 | 图文混合检索 |
| `tongyi-embedding-vision-plus-2026-03-06` | 64~1152 | 1,024 | 融合 + 独立 | 跨模态搜索 |
| `tongyi-embedding-vision-flash-2026-03-06` | 64~768 | 1,024 | 融合 + 独立 | 跨模态搜索（省成本） |
| `tongyi-embedding-vision-plus` | 64~1152 | 1,024 | **仅独立** | 文搜图、图搜图 |
| `tongyi-embedding-vision-flash` | 64~768 | 1,024 | **仅独立** | 文搜图、图搜图 |
| `multimodal-embedding-v1`（**当前在用**） | — | — | **仅独立** | 旧版 |

**关键区分**：
- **融合向量**：把 text + image 放进**同一个 content 对象**（或用 `enable_fusion=true`），
  输出**一个**向量 → 图文天然在同一位置，不存在"搜不到"
- **独立向量**：文本、图片各自成向量 → 依赖模型自身的跨模态对齐能力

我们现在用的 `multimodal-embedding-v1` 属于**独立向量**路线。
这就解释了第 1 节的实测结论（文本→图距离 0.885、排第 190/290）：
**它是设计成"两个独立空间做跨模态匹配"的，而这个匹配在我们的实测里基本失效。**

### 1.2 但在 Dify 里用不上融合向量（两个硬约束）

**约束一：Dify 通义插件只暴露了 `multimodal-embedding-v1`**
插件源码 `models/text_embedding/text_embedding.py` 里硬编码：

```python
def call_embedding_api(text):
    if model in ["multimodal-embedding-v1"]:
        return dashscope.MultiModalEmbedding.call(...)   # 只有这一个模型走多模态接口
    else:
        return dashscope.TextEmbedding.call(...)         # 其它走纯文本接口
```

即使把 `qwen3-vl-embedding` 作为自定义模型加进去，文本侧也会走错接口。
要用上它必须**自研 Dify 插件**。

**约束二（更根本）：Dify 的数据结构里没有"融合向量"的位置**
Dify 的索引模型是固定的：

```
每个 segment  → 1 个文本向量
每个 attachment → 1 个独立图片向量
```

`create_segments_vector` 只接收文本；`create_multimodal` 只接收附件。
**没有任何地方可以存放"某一段正文 + 它的图"融合成的那一个向量。**
所以即便写了插件，Dify 也存不下融合向量。

### 1.3 因此建议改走「图片语义文本化」路线

既然跨模态检索这条路在 Dify 里走不通，正确的做法是**把图片的语义转成文本**：

```
图片 ──(轻量视觉模型)──► 结构化描述文本
                            │
                     与图注 + 章节路径拼接
                            │
                   作为 segment 正文的一部分入库
                            │
             图片本身仍作为 attachment 绑定在同一个 segment 上
```

**这样做有三个好处**：

1. **图片变得可检索**——它的语义进入了文本向量空间，不再是"距离 0.885 的孤岛"
2. **可以用最强的文本 embedding 模型**——目前为了"多模态"被迫用 `multimodal-embedding-v1`，
   而它的文本检索能力很可能不如专用的 `text-embedding-v4` / `qwen3.7-text-embedding`。
   图片语义文本化后，**文本侧可以换成最强的文本模型**，检索质量直接提升
3. **不需要改 Dify**——完全在 Dify 现有能力内实现

图片依然作为 attachment 返回给视觉 LLM，所以"模型能看图"这件事不受影响。

> **结论**：把"多模态检索"的责任从 embedding 模型转移到**入库前的语义标注**上。

## 二、轻量视觉模型选型（图片语义标注用）

从本机已装的通义/DeepSeek 插件中筛选带 `vision` 的模型，按成本排序：

| 模型 | 上下文 | 输入价（元/千token） | 输出价 | 备注 |
| --- | --- | --- | --- | --- |
| **`qwen3.7-flash`** | 1M | **0.0002** | 0.0008 | 最便宜，通用模型带视觉 |
| **`qwen3-vl-flash`** | 131K | 0.0005 | 0.002 | **专用 VL，推荐** |
| `qwen3.8-flash` | 1M | 0.0008 | 0.0027 | 带 structured-output |
| `qwen3.6-flash` | 1M | 0.0012 | 0.0072 | |
| `qwen3-vl-plus` | 262K | 0.001 | 0.01 | 更强 |
| `qwen-vl-max` | 131K | 0.0016 | 0.004 | |
| `deepseek-flash` | 1M | 插件未标价 | — | 带 vision |

**建议**：主用 **`qwen3-vl-flash`**（专用视觉、便宜），
需要结构化 JSON 输出时用 `qwen3.8-flash`（带 `structured-output`）。

**成本估算**：101 张图 × 约 (1K 输入 + 300 输出) ≈ **0.1 元量级**，可忽略。

## 三、MinerU 无 GPU 可行性

### 3.1 调研结论（含来源）

| 问题 | 结论 |
| --- | --- |
| 纯 CPU 能跑吗 | **能**。MinerU 4.0 官方 Release 原文：「基础包开箱即用：小模型走 ONNX CPU，VLM 使用 llama.cpp Vulkan 模式」 |
| 哪些档能跑 | 4.x 全部档位都有 CPU 路径；**2.x/3.x 只有 `pipeline` 后端支持 CPU**，`vlm-*` 必须 GPU |
| 3.x 陷阱 | 3.4 的 `DEFAULT_BACKEND=hybrid-engine`（需 GPU），**不显式传 `backend=pipeline` 必失败**，且环境变量覆盖不了（4.x 已修复） |
| CPU 硬门槛 | **AVX2 必需**。官方 FAQ 第 7 条：`Illegal instruction` 的成因就是 CPU 不支持/禁用 AVX/AVX2 |
| 速度 | 16 核 CPU VM：22 页 ≈30 s（≈1.4 s/页）；x86 公式密集页 ≈16 s/页；ARM 鲲鹏 >300 s/页。**→ 100 页乐观 ≈2.5 分钟，公式/表格密集 20–30 分钟** |
| 内存 | 官方**最低 16GB、推荐 32GB+**；社区实测跨文档 RSS 增长 +0.47 GiB/篇，可用 `MALLOC_TRIM` 压低 |
| 精度 | onnx 与 torch 是**同一套模型两种格式**（非降级）；真实差距在档位：pipeline 86.47 vs VLM 95.30 |

> 来源：`04_MinerU无GPU调研.md`（含逐条链接与"未找到可靠数据"标注）

### 3.2 本机实测（已实际执行）

我在这台机器上真的装了并跑起来了：

| 步骤 | 结果 |
| --- | --- |
| 安装 `mineru==4.0.7` | ✅ 989 MB，**依赖里没有 torch**（确认走 ONNX + llama.cpp） |
| 下载 basic 档模型 | ✅ 13 个文件、35 秒（含 PP-FormulaNet_plus-M 591 MB） |
| 启动本地 parse-server | ✅ 成功（PID 起来，tier=basic） |
| 加载 ONNX 模型 | ✅ **`providers=['CPUExecutionProvider']`**（layout/OCR/表格模型全部加载成功） |
| 执行 `mineru parse` | ❌ 失败于 `multiprocessing.Lock()` → `PermissionError` |

**失败根因（重要）**：MinerU 的 PDF 渲染阶段用了 `multiprocessing`，
而 Python 多进程的 semaphore 需要写 `/dev/shm`。**我的执行沙箱不允许写 `/dev/shm`**，所以失败。

```
File ".../multiprocessing/synchronize.py", line 57, in __init__
PermissionError: [Errno 13] Permission denied
```

**这是我这边环境的限制，不是 MinerU 的问题。** 但它暴露一个真实的部署注意点：

> **在 Docker 里跑 MinerU 必须给足 `/dev/shm`**（`--shm-size`）。
> Docker 默认只有 64MB，属于这类 `PermissionError` / `Bus error` 的经典成因。
> 同理，任何容器化的文档解析（MinerU / PaddleOCR / unstructured）都要注意这一点。

### 3.3 本机硬件评估

| 项 | 实测值 | MinerU 要求 | 判定 |
| --- | --- | --- | --- |
| CPU | i5-13500HX，10核20线程，**有 AVX2，无 AVX-512** | 需 AVX2 | ✅ 满足 |
| 内存 | 15 GB 总 / **可用 11 GB** | **最低 16 GB** | ⚠️ **低于最低要求** |
| GPU | 无（VM，NVML 被屏蔽） | 4.x CPU 路径不需要 | ✅ 可接受 |

**结论**：这台机器能跑 MinerU CPU，但**内存偏紧**（11GB < 官方 16GB 最低）。
100 页可能触发 OOM，需要用 `MINERU_MALLOC_TRIM` 等参数压制 RSS 增长，
或**只处理小批量页**。

## 四、PaddleOCR 路线

你提到走 API 服务，正好对应 **PaddleOCR 官方 API**：

- SDK：`paddleocr` 包里的 `PaddleOCRClient` / `AsyncPaddleOCRClient`
- 认证：`PADDLEOCR_ACCESS_TOKEN`（从 [AI Studio](https://aistudio.baidu.com/account/accessToken) 获取）
- 模型可选项：`OCROptions` / `PPStructureV3Options` / **`PaddleOCRVLOptions`**
- 特点：**提交任务到官方托管服务，不在本地推理、不加载本地模型**

这条路完全规避了硬件问题，也能拿到 PP-StructureV3 的**单元格级坐标**
（`overall_ocr_res`，这是 PaddleOCR-VL 所没有的）。

## 五、下一步：小规模对照测试方案（P0）

### 5.1 目标

在同一份材料（**第 11–20 页**，含人工呼吸图、胸外按压图、接地保护图，图注问题最典型）
上对比两套方案，**用数据决定选型**，而不是凭印象。

### 5.2 评测维度（每项都要能落到数字）

| 维度 | 判定方法 | 为什么重要 |
| --- | --- | --- |
| **图注配准率** | 每张图是否与其图注（「图 N-M ...」）在同一输出块内 | 当前 51% 错配，这是头号问题 |
| **图片位置保真** | 输出是否给出图片 bbox / 阅读顺序位置 | 决定能否精确绑定到正确段落 |
| **小节边界** | 输出是否有标题层级，能重建章节树 | 决定能否做"整节上下文" |
| **表格/公式** | 表格是否还原为结构化形式、公式是否 LaTeX | 教材含大量公式与表格 |
| **阅读顺序** | 多栏排版下顺序是否正确 | 影响切分连贯性 |
| **速度** | 10 页耗时（分钟） | 决定 100 页是否可接受 |
| **资源** | 峰值内存 | 本机 11GB 可用，是硬约束 |

### 5.3 产出

一份对照表 + 明确结论：选 MinerU 还是 PaddleOCR（或两者分工）。

## 六、需要你提供的东西

### 必需

1. **PaddleOCR 官方 API 的 Access Token**
   从 https://aistudio.baidu.com/account/accessToken 获取。
   没有它无法跑 PaddleOCR 这一侧。

2. **百炼 API Key**（明文，用于我写脚本直接调）
   用途：
   - 轻量视觉模型为 101 张图生成语义描述
   - 换用更强的文本 embedding 模型做对比
   - 若走 ParseX 还要用它调文档解析
   > Dify 里配置的是加密存储，我取不出来，需要你给一个可用的 Key（可设额度上限）。

### 需要你决定

3. **MinerU 走哪条路**：
   - **A. 本地 CPU**——本机内存 11GB 低于官方最低 16GB，有 OOM 风险；且我的沙箱不能写 `/dev/shm`，
     **需要你在自己的终端跑**（我可以给一键脚本）
   - **B. MinerU 官方 API**——需要 mineru.net 的 token；官方有免费额度
   - **C. 先在你自己机器上跑本地版**（推荐，能顺便验证你那边的内存是否够）

4. **两级分块的粒度目标**：
   - 父块 = **小节**（如「1.4.1 防止机械损伤」）还是**整章**？
   - 子块 = **段落**还是**列表项/表格**？
   > 我的建议：父块 = 最小一级小节，子块 = 段落/列表项。这样既能整节召回，又不丢精度。

5. **图片描述的粒度**：
   - 只描述"画了什么"（廉价、够用）
   - 还是要包含"图中标注的文字、数值、符号"（OCR 式，更贵但电路图/表格截图必须）

### 可选（有则更好）

6. 是否希望我顺带测 **`qwen3-vl-rerank`**（多模态重排序）——它不在 Dify 通义插件里，
   但如果自己做检索层可以用上
7. 是否有**目标问答集**（10–20 个"问题 + 期望答案"），
   这样重建后能做**可量化的 A/B 对比**，而不只是看个案
