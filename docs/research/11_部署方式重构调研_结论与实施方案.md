## 0. 结论

**不建议重写核心。建议重构"生命周期 / 供给"这一层。**

三句话：

1. **故障不在领域核心，在部署生命周期层。** 两轮 14 个问题里，**全部 3 个"阻断级"问题**（让全新部署失败或假成功的）
   都落在生命周期/供给层；核心的解析→分块→标注→向量化→检索链路两轮都是通的 `[实测]`。
2. **核心的"零第三方依赖"是真资产，且被验证过。** `multimodal_kb/` 全域 **0 个第三方 import**（只有
   stdlib：`urllib`/`http.server`/`argparse`/`dataclasses`…）`[代码]`。为修部署而放弃它是**误伤**。
3. **但"零依赖"被错误地扩张到了运维层**，而赔钱的地方正在那里：手写健康探针语义、手写 shell 初始化编排、
   两份 `.env` 解析实现。收缩这条约束的**适用范围**，比增加依赖更重要。

> 最重要的单条建议：**先补"全新环境"自动化测试，再动结构。**
> 两轮的阻断级问题（P1/R1）**只在干净环境暴露**，而仓库里既没有 CI（`.github/` 不存在 `[实测]`），
> 也没有可用的干净安装测试。不补这一环，任何重构都会以同样方式烂掉。

## 1. 先量化"故障率"：问题到底出在哪一层

把两轮的全部 14 个问题按层归类：

| 层 | 问题 | 数量 | 最严重级别 |
| --- | --- | --- | --- |
| **L3 生命周期 / 供给** | P1 入库不建集合、P3 容器 root 属主、P5 适配器未进镜像、N1 镜像无 curl、N4 产物复用不校验、N5 源码权限、**R1 全新部署死锁**、**R2 清理假成功** | **8** | 🔴 阻断 |
| L1 领域核心 | N2 融合向量维度回退、N3 `ImageRef` 误传、P4b 缓存 key 含绝对路径、R3 `http.client` 丢代理、R5 校验分支漏、R6 大文件全量读 | 6 | 🟠 中 |
| L2 服务契约 | P2 自检假绿 / `/health` 吞异常、R4 探针 3 次往返 + exact count | 2 | 🟠 中 |
| L4 文档 / 配置一致性 | P4 `.env` 不自动加载、P6 重复定义、文档与实现不符 | 3 | 🟡 低 |

（合计 >14 因为 P2 同时算 L2/L4、R2 同时算 L2/L3。）

**关键分布**：

- **阻断级 3 个（P1、R1、R2）全部在 L3/L2，没有一个在领域核心。**
- L3 只有 **467 行**（`deploy/` + `Makefile` + `kb`）`[实测]`，却是故障密度最高的一层。
- L1 的 6 个里有 3 个（N2、N3、R3）是**在修部署的过程中新引入或才暴露的**，不是原有架构缺陷。

**结论**：故障密度与代码量的比值在 L3 严重失衡 → 应重构 L3，而不是重写 L1。

## 2. 四个根因（不是"脚本写得烂"，是结构问题）

### 根因 A：初始化没有归属（no owner for the init phase）

`kb init` 是一个**可选 CLI 命令**，不属于任何生命周期。于是"建集合"这件事被实现了**三次**：

| 实现位置 | 是否调 `init_store()` |
| --- | --- |
| `cli/main.py:437 cmd_ingest` | ❌ 原来漏了 → **P1** |
| `scripts/ingest.py:74` | ✅ |
| `deploy/deploy.sh:129`（shell） | ✅ 但放错位置 → **R1** |

`[代码]` 三个独立入口实现同一件事 → **必然漂移**。P1（两个 Python 入口行为不一致）和 R1（shell 里
第三个实现，且顺序错误）是同一个根因的两次发作。

**业界做法**：Dify 用一次性 init 容器 + marker file + `restart:"no"`；RAGFlow 把
`ensure_db_init` 提到**所有**服务启动之前，其 entrypoint 注释亲口记录了同类 bug：
*"This used to run inside the web server block only, so hosts that ran e.g. just the admin server,
data sync, MCP server, or task executors never initialized the schema."* `[业界]`

### 根因 B：安全属性放错层（safety property in the wrong layer）

非 root 运行这件事被放在 **compose `user:`** 里，而不是**镜像**里：

- `deploy/Dockerfile` **没有 `USER`** `[代码]` → 镜像默认 root。
  只有走 `deploy.sh` / 本项目 compose 才安全；换 k8s、podman、`docker run` 立刻退回 root，P3 复发。
- 我实测其脆弱性：**改用 named volume 时，`user: "1000:1000"` 直接崩**
  （`PermissionError: '/data/work'` —— 卷由 root 建，uid 1000 写不进）`[实测]`。
  也就是说这个修复**只对"宿主预建目录的 bind mount"这一种形态有效**。
- 同类问题还有**端口默认值三处并存**：`config.py` 读 `MMKB_PORT`、Dockerfile CMD 硬编码 `--port 8088`、
  compose `ports: "${MMKB_PORT}:8088"` → `MMKB_PORT` 的语义在三处不一致 `[代码]`。

**业界做法**：Milvus 用 `milvus-volume-init` 一次性容器专门做 `chown -R` + marker file `[业界]` —— 
**和我们 P3 完全同构的问题，业界的解法是把 uid 治理变成一个显式的初始化步骤**，而不是散在编排参数里。

**但对我们这个栈，有一个更彻底的解法，而且推翻了一个流传的假设。**
`docker-compose.yml:41` 的注释写着"Qdrant 官方镜像不支持非 root 启动" —— **这句是错的** `[实测]`：

```
$ docker manifest inspect qdrant/qdrant:v1.19.1-unprivileged  -> EXISTS
$ docker manifest inspect qdrant/qdrant:latest-unprivileged   -> EXISTS
$ docker inspect mmkb-qdrant -f '{{.Config.User}}'            -> 0:0   # 我们确实在跑 root
```

Qdrant 上游用同一份 Dockerfile 通过 `--build-arg USER_ID=1000` 发布 `-unprivileged` 变体，
并持续维护（v1.19.1-unprivileged 等）`[业界]`。**换成这个 tag + 宿主 uid，root 属主文件这一类问题
（P3、R2 以及 `make distclean` 的所有绕路）会整体消失**，不需要任何 chown 技巧。
这是"安全属性应该进镜像/进组件选型，而不是靠编排层打补丁"的又一个例证。

我把它跑通验证了（宿主属主目录做 bind mount，**不加任何 `user:` 覆盖**）`[实测]`：

```
root image:     Config.User = 0:0
unprivileged:   Config.User = 1000:1000        ← 安全属性在镜像里，不在编排参数里

$ docker run -v /tmp/qd-unpriv/storage:/qdrant/storage qdrant/qdrant:v1.19.1-unprivileged
  /readyz          -> HTTP 200  all shards are ready
  container user   -> uid=1000(qdrant) gid=1000(qdrant)
  root 属主文件数   -> 0        （宿主属主条目 5）
```

对比之下，我们**当前**的修复方式（compose `user:` + 宿主预建目录）在换成 named volume 时直接崩 `[实测]`
—— 同样的目标，一个靠组件选型达成，一个靠编排约定维持，健壮性差一个量级。

### 根因 C：存活与就绪被混为一谈

`/health` 同时承担 liveness 和 readiness `[代码]`：

- 它做 3 次 Qdrant 往返（含 `exact: true` count）；compose 健康检查超时只有 5s 且不可配 `[代码]`。
- 依赖抖动 → 容器被判 unhealthy → `restart: unless-stopped` 语境下是 **restart storm**，而不是"摘流量"。
- 而 `deploy.sh` 又把"就绪"当作"存活"来等 → **R1 死锁**：集合要 init 才存在，init 要等就绪，就绪要集合存在。

我还实测了一个相关事实：**Qdrant 不可达时服务照样启动并对外服务**，只是永远 503 `[实测]`：

```
$ docker run -e QDRANT_URL=http://qdrant-does-not-exist:6333 mmkb/service:latest
  Up 5 seconds
  /health -> HTTP 503 {"qdrant_reachable": false, "status": "degraded", ...}
```

即"起来了但永远答不了任何查询"。这正是探针语义含糊的代价。

**业界做法**：Qdrant 官方提供 `/livez` / `/readyz` / `/healthz`（v1.5.0+，且不受 API key 影响）
`[业界]`；我实测本机 Qdrant **1.19.1** 的 `/readyz` 返回 `all shards are ready` `[实测]`。
而当前 compose 用的是 `bash -c ':> /dev/tcp/127.0.0.1/6333'` —— **只探 TCP 端口是否打开** `[代码]`，
放着官方就绪探针不用。

### 根因 D（过程）：没有"全新环境"测试，没有 CI，文档手抄命令

- 仓库**没有 `.github/`**，即**没有任何 CI** `[实测]`。
- `tests/smoke_test.py` 的前置条件是"Qdrant 在跑 + 服务已启动 + **库里有数据**"，
  且 `tests/` 下**没有 fixture PDF** `[实测]` → 无法在干净环境自动跑。
- 于是两轮阻断级问题都是**人工在新机器上踩出来的**：P1 在报告一、R1 在报告二，
  且**只有"真全新"才触发**（重复执行 `deploy.sh` 时集合已存在，路径是通的 → 作者复测没发现）。
- 文档手抄命令 → 必然漂移：`docs/deployment.md:314` 写"`make distclean` 已经用一次性容器来清理"，
  而实现里那个分支**永远不会被走到**（判据是 `[ ! -w data/qdrant ]`，但 `data/qdrant` 目录本身一直是宿主机用户的），
  实测结果是**删掉一半还报成功** `[实测]`。

## 3. 实证：推荐方案能不能修好 R1？

用**当前未改动的代码**，在隔离环境做 A/B（独立 project、独立卷、独立端口，不碰你的运行栈）`[实测]`：

**A) 当前设计**（app + qdrant，无初始化步骤，`up --wait`）：

```
Container mmkbab-broken-qdrant-1 Healthy
application not healthy after 45s
EXIT=1
```

**B) 建议设计**（加入一次性 init 服务 + `condition: service_completed_successfully`，同一条 `up --wait`）：

```
Container mmkbab-fixed-init-1   Exited
Container mmkbab-fixed-qdrant-1 Healthy
Container mmkbab-fixed-mmkb-1   Healthy
EXIT=0

$ curl -s localhost:18089/health
{"collection":"mmkb","qdrant_reachable":true,"collection_exists":true,"points":0,"status":"ok"}

SERVICE   STATUS
init      Exited (0)
mmkb      Up (healthy)
qdrant    Up (healthy)
```

**结论**：同一份镜像、同一个"全新空库"，把初始化从 shell 提升为**声明式的一次性服务**后，
死锁消失，**且不需要任何 shell 轮询循环**（`docker compose up -d --wait` 直接给出 exit 0 / 非 0）。
我还验证了该模式在本机 Compose 版本下语法可用（`docker compose config` 通过），
以及 `kb init` **本身幂等**（重复执行输出"集合已存在: mmkb（0 点）"）`[实测]`。

**C) 更好：本机 Compose 已支持原生 init 容器 `pre_start`。**
Docker 官方文档已把 one-shot service 模式标注为"可被 `pre_start` 取代"；`pre_start` 需要 Compose ≥ v5.3.0，
而本机是 **v5.5.1**，正好可用 `[实测]`。同一条 `up --wait`、同样全新空库：

```
$ docker compose -f compose-prestart.yaml up -d --wait --wait-timeout 90
 Container mmkbab-prestart-qdrant-1 Healthy
 Container mmkbab-prestart-mmkb-1 Healthy
EXIT=0

$ curl -s localhost:18091/health
{"collection":"mmkb","qdrant_reachable":true,"collection_exists":true,"points":0,"status":"ok"}
  ↑ 集合是那个临时 pre_start 步骤建的

$ docker compose ps -a
  mmkb: Up (healthy)     qdrant: Up (healthy)     ← 没有"已退出的服务"污染 ps
```

加在 mmkb 服务上只有两行，且**不需要**在服务之间织 `depends_on` 边：

```yaml
  mmkb:
    depends_on: {qdrant: {condition: service_healthy}}
    pre_start:
      - command: ["kb", "init"]      # 必须幂等
```

**最终推荐：优先 `pre_start`，把 `service_completed_successfully` 作为 Compose < v5.3 的兜底。**
两者都依赖同一个前提：**`kb init` 必须幂等**（`up` 会重复触发它）`[业界]`。

⚠️ 三个必须记住的坑（均有一手来源）`[业界]`：

1. **`--wait` 遇到 `unhealthy` 是"立即报错"，不是等到 `--wait-timeout`** ——
   所以把"集合是否存在"塞进健康检查，会让 503 直接中断启动。这正是 R1 的机制。
2. **一次性服务若没有任何人用 `service_completed_successfully` 依赖它**，`--wait` 会按
   `running_or_healthy` 等它 → 它退出（哪怕退出码 0）也会让 `--wait` 失败并报 `container X exited (0)`。
   所以 init 服务**必须**被显式依赖（上面 B 实验里它是，所以通过了）。
3. **`--wait` 与一次性容器的兼容是 docker/compose PR #9572 才修好的**（此前会永久挂起）→
   `deploy.sh` 应校验 `docker compose version`，文档写明最低版本。

## 4. 业界对照：值得抄的与要避开的

| 项目 | 初始化 | 依赖门控 | 可抄的点 |
| --- | --- | --- | --- |
| **Dify** | `init_permissions` 一次性容器：marker file 幂等 + `restart:"no"` | `service_completed_successfully` + `required:false` | 一次性 init 容器；`.env.example` 只放"能启动所必需"的变量；可选服务全靠 profiles |
| **Milvus** | `milvus-volume-init`：`chown -R` + marker file | `service_completed_successfully` | **uid/chown 作为显式初始化步骤**（正对我们 P3） |
| **RAGFlow** | `ensure_db_init` 提到所有服务之前 | 只门控 mysql/nats，不门控 ES | entrypoint 注释记录了"init 只在某 profile 里跑"的 bug |
| **Onyx** | `command: alembic upgrade head && uvicorn` | `service_started` | `start_period: 600s`，注释写明"免得 `up --wait` 在迁移期间判 unhealthy" |
| **Zitadel** | `start-from-init`（幂等启动，无独立迁移服务） | `service_healthy` | 把 init 折进进程启动 |
| **Verba** | 无 init | app `service_healthy` ← weaviate `service_healthy` | 双方都有真探针 |
| **Qdrant 官方** | 不提供 init 容器；推荐 app 侧 `exists → create` | — | `/livez` `/readyz`；`GET /collections/{name}/exists`（v1.8.0+） |

**反模式（都有出处）**：

1. **短式 `depends_on` 不是就绪**。Docker 官方原文："Compose does not wait until a container is 'ready',
   only until it's running."
2. **健康检查跨服务边界**（`pg_isready -h db_postgres`、以及在探针里跑 `CREATE DATABASE`）→ 依赖没就绪时
   自己的探针失败，正是"unhealthy because dependency not ready"这一类。
3. **init 埋在某一个 profile 的 entrypoint 里** → 其它 profile 静默不初始化（RAGFlow 的原始 bug）。
4. **`deploy.sh` + 手写轮询作为排序机制** —— 本项目的 R1 就是它的直接后果。

## 5. 目标架构

### 5.1 Compose 分层（依赖图显式化）

```
qdrant        : service_healthy   (换 -unprivileged 镜像 + 探针用官方 /readyz)
   │  service_healthy
mmkb          : service_healthy   (探针指 /livez)
   ├─ pre_start: ["kb", "init"]    ← 原生 init 容器（Compose ≥ v5.3；本机 v5.5.1 实测可用）
   │                                  与 kb CLI 共用同一函数，shell 里不再有第三份实现
   └─ 启动钩子再兜一次 ensure_schema（单副本形态下）
   │
openwebui     : profiles: [chat]  ← 可选件永不进入核心 depends_on 链
```

### 5.2 健康端点拆分（P0，零新依赖）

| 端点 | 语义 | 行为 | 谁消费 |
| --- | --- | --- | --- |
| `GET /livez` | 存活 | **不碰任何外部依赖**，进程活着即 200 | **compose `healthcheck`**、重启判定 |
| `GET /readyz` | 就绪 | Qdrant 可达 + 集合存在 + schema 版本匹配 + count（缓存 30s）；未就绪 **503** + 原因 | `deploy.sh` 的收敛断言、外部 LB / 监控 |
| `GET /health` | 兼容别名 | 等同 `/readyz` | 老调用方；不要再赋予第三种含义 |

**注意一个反直觉之处：compose 的 `healthcheck` 应当指向 `/livez`，而不是 `/readyz`。**
理由 `[业界]`：在非 Swarm 的 Compose 里，健康状态**既不驱动重启也不摘端口**，它只被
`depends_on: service_healthy` 和 `up --wait` 消费。把就绪塞进它，等于让"依赖抖动"变成
"启动失败"（就是 R1）；而真正的流量门控本来就该由 LB/监控看 `/readyz`。
所以：**healthcheck = 存活（`/livez`），就绪由 `deploy.sh` 里一次独立的 `/readyz` 断言负责**。

`verify.sh` 与 `deploy.sh` 的断言都指向 `/readyz`，`/health` 保留为兼容别名。

### 5.2b 卷策略（P1，零新依赖）

| 目录 | 用哪种卷 | 为什么 |
| --- | --- | --- |
| `data/qdrant`（向量库） | 可以改用 **named volume**；若要宿主直连备份，则 bind mount + **unprivileged 镜像** + 匹配 uid | Qdrant 官方明确不支持 NFS/S3，且警告 WSL 挂载会丢数据 `[业界]`。named volume 能整体消灭属主问题 |
| `data/work`、`data/parsed`（宿主 CLI 与容器都要碰） | **必须 bind mount** | named volume 只有容器内可达；且**跨文件系统的原子 rename 会报 `EXDEV`** —— 将来若把缓存写入改成 `os.replace()` 临时文件再改名，named volume 会直接坏掉 `[业界]`。两侧同 uid 即可 |

清理脚本的正确写法（据此重写 `distclean`）`[业界]`：

```bash
uid=$(id -u)
# 判"树里有没有别人的文件"，绝不要 [ -w "$dir" ]（那只测挂载点自身）
if find "$target" -xdev \( ! -user "$uid" -o \( -type d ! -writable \) \) -print -quit | grep -q .; then
    docker run --rm -v "$data_dir:/data" alpine:3.20 sh -c 'rm -rf /data/qdrant'   # 挂父目录、删子目录
else
    rm -rf -- "$target"
fi
[ -z "$(find "$target" -mindepth 1 -print -quit)" ] || { echo "清理失败" >&2; exit 1; }  # 复核，别信 $?
```

三个细节：**不要挂载正要删除的目录本身**；**不要用 `dir/*`**（漏 dotfile，空目录还会留下字面 glob）；
**不要 `|| true` / `2>/dev/null` 吞掉删除的退出码** —— 这一点需要更正我上一轮的表述：
`rm -rf` 其实**如实返回了 exit 1**（POSIX 规定只有每个条目都删成功才返 0），
是**脚本**用 `2>/dev/null || true` 把这个信号销毁了，然后打印"已清空"。所以 R2 的根因是
"脚本丢弃退出码 + 判据看错对象"，而不是 `rm` 说谎 `[业界]`。

### 5.3 镜像纪律（P1，零新依赖）

- `deploy/Dockerfile` 加 **`USER 10001`**（安全属性进镜像，不只进 compose）。
- **Qdrant 换 `qdrant/qdrant:<版本>-unprivileged`**，并给它 `user: "<宿主uid>:<宿主gid>"` `[实测]`。
  这样 `data/qdrant` 不再产生 root 属主文件，**根因 B 的一半直接消失**：
  不需要 Milvus 式的 chown init 容器，也不需要 `make distclean` 的一次性容器绕路。
- 端口只有**一个来源**：镜像 CMD 不再硬编码 `--port 8088`，改为读 `MMKB_PORT`。
- **钉死第三方镜像**（现在是 `qdrant/qdrant:latest`、`open-webui:main` `[代码]`）。
  本机拉到的 Qdrant 已是 **1.19.1**，而代码注释里写着 1.19 专属的兼容处理 `[代码]`——
  `latest` 意味着"今天装的和下月装的可以不是一个东西"，这是可复现性的直接漏洞。
  钉版本也顺带把"-unprivileged"这个 tag 固定下来。
- 适配器改为独立发行包 + `entry_points`（**`importlib.metadata` 是标准库**，与"核心零依赖"不冲突），
  镜像构建时 `pip install . ./integrations/dify` 装进同一 venv —— 从而**删掉**
  `COPY integrations /app/integrations` + `chmod -R a+rX` 这套兜底（它本身就是权限问题的来源之一）。

### 5.4 配置单一事实源（P1，零新依赖）

- **两份 `.env.example` 合并成一份**（现在根目录与 `deploy/` 各一份且内容不同 `[实测]`），
  `kb` 里那段手写 bash `.env` 解析器删除（这是第二份 `.env` 语义实现）。
- `KBConfig.validate()` **fail-fast 且一次报全部问题**，调用点在进程启动边界。
  顺手修一个实测到的真 bug：

  ```
  MMKB_PORT=80a8  →  service_port = 8088   # config.py:46 静默吞掉 ValueError  [实测]
  ```

### 5.5 schema 演进（P1，零新依赖）

不引入迁移框架，但补纪律：`SCHEMA_VERSION` + 集合内**哨兵点**存指纹

## 8. 验收标准：部署契约测试矩阵

把"部署正确"从散文变成**可执行的断言**（这是防复发的关键）：

| # | 场景 | 断言 | 能抓住 |
| --- | --- | --- | --- |
| 1 | **全新安装**（无 data、无集合） | `up -d --wait` 退出码 0；`/readyz` 200；`kb docs` 为空 | **P1、R1** |
| 2 | 重复执行（幂等） | 再跑一次退出码 0，点数不变 | 幂等性回归 |
| 3 | 升级（已有数据 + 新镜像） | 点数不减；`schema_version` 兼容或显式报错 | 迁移纪律 |
| 4 | 清理 | 清理后 `data/qdrant` 确实为空；退出码 0 | **R2** |
| 5 | 宿主 CLI ↔ 容器混合使用 | 宿主 `kb ingest` 不报 `PermissionError` | **P3** |
| 6 | 健康契约 | Qdrant 不可达 → `/livez` **仍 200**、`/readyz` **503**；集合缺失 → `/readyz` 503 且 `collection_exists:false` | **P2、R4、C 根因** |
| 7 | 配置校验 | `MMKB_PORT=80a8` → 启动失败并明确指出该变量 | `_env_int` bug |

场景 1、4、5 必须在 **CI 的干净 runner** 上跑。具体做法 `[业界]`：

- GitHub 托管 runner 每次都是**全新 VM**；起手与收尾都 `docker compose down -v --remove-orphans`（收尾放 `if: always()`）；
- 用 `COMPOSE_PROJECT_NAME=mmkb-ci-${{ github.run_id }}` **隔离项目名**，避免并行 job 抢卷抢端口；
- **分两个 job**：`fresh-install`（无任何卷，直接 `up -d --build --wait --wait-timeout 300` —— init 坏了这一步就红）
  和 `upgrade`（先入库，再**不带 `-v`** 地 `up` 一次，断言 init 幂等且数据存活）。后者才能抓住"`kb init` 不幂等"；
- 失败时收集 `docker compose ps -a` + `logs` 作为 artifact；
- 缓存 buildx 层，**绝不**缓存 Qdrant 卷。

另外需要一个**小 fixture PDF**（`tests/` 下现在没有 `[实测]`），让 fresh-install job 能顺带跑一次极小的入库。
