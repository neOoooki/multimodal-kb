# 架构

## 全景

```
  PDF
   │
   │ ① 解析（MinerU）
   ▼
  结构化块序列 ── 类型 / bbox / 图注 / 表格 HTML / 阅读顺序
   │
   │ ② 结构重建 + 两级分块
   ▼
  父块（小节） + 子块（段落/列表/表格）
   │
   │ ③ 图片语义标注（qwen3-vl-flash）
   ▼
  子块正文 = 【章节路径】 + 正文 + 图注 + 图片描述
   │
   │ ④ 三路向量化
   ▼
  ┌──────────────────┬──────────────────┬──────────────────┐
  │ fusion 2560      │ text 1024        │ image 2560×N     │
  │ 正文+图 → 1 个向量│ 正文+图片描述     │ 每张图各自成向量   │
  └──────────────────┴──────────────────┴──────────────────┘
   │
   │ ⑤ 存入 Qdrant（一个 chunk = 一个 point，带 3 个具名向量）
   ▼
  Qdrant
   │
   │ ⑥ 检索：多路并行 → RRF 融合 → rerank
   ▼
  检索服务（HTTP）
   │
   ├─► integrations/openwebui   Pipe Function（确定性注入图片）
   ├─► integrations/dify        HTTP 节点 / External Knowledge API
   └─► 你自己的前端
```

## 为什么这样设计

### 1. 核心不依赖任何 chat 框架

`multimodal_kb/` 是一个**独立的 Python 包**，不知道 Dify / Open WebUI 的存在。

原因：Dify 的索引结构是「每 segment 一个文本向量 + 每附件一个图片向量」，
**存不下"正文+图融合成的那一个向量"**。如果按它的能力设计模型，
就等于把它的缺陷固化进核心。

所以核心的 `Chunk` **完整保留**所有信息（图片对象、bbox、章节树、表格 HTML），
由 `integrations/` 里的适配器负责降级映射 —— 丢什么、怎么丢是适配器的责任。

换框架只写新适配器，核心一行不改。

### 2. 为什么是三路向量

实测（20 组有标准答案的图文对，文→图 Top-1）：

| 方案 | Top-1 |
| --- | --- |
| `multimodal-embedding-v1`（多数 RAG 平台用的） | **40%** |
| `tongyi-embedding-vision-plus` | **40%**（同代换型没用） |
| `qwen3-vl-embedding` 独立向量 | 80% |
| **`qwen3-vl-embedding` 融合向量** | **95%** |
| `qwen3-vl-rerank` 重排 | 90% |

**融合向量最强，但普通 RAG 平台存不下**。本平台三路并存：

| 向量 | 用途 | 为什么需要 |
| --- | --- | --- |
| `fusion` | 正文+图 → 1 个向量 | 跨模态最强（95%） |
| `text` | 正文+图片描述 | 不依赖跨模态对齐；可用最强文本模型 |
| `image` | 每张图各自成向量（multivector, `max_sim`） | 以图搜图 |

### 3. 为什么还要把图片"文本化"

融合向量虽好，但如果目标框架存不下它，跨模态检索就退化成 40%。

所以流水线**同时**把图片语义转成文本（`qwen3-vl-flash` 生成详细描述），
写进子块正文。这样即使只走 `text` 一路，图片语义依然可被检索到。

两条路互为备份：

```
图片 ──┬─► 融合向量（跨模态）        ← 最强
       └─► VLM 描述 → 文本向量       ← 兜底，且不依赖跨模态能力
```

### 4. RRF 而不是加权求和

各路的**分数量纲完全不同**（融合向量余弦 0.9、RRF 分 0.03）。
RRF 只用**排名**：

```
分数 = Σ 1 / (k + 该路排名)      k = 60
```

所以不同量纲可以安全融合，不需要调权重。

### 5. rerank 的价值

embedding 是"双塔"：query 和 document **各自独立编码、从不"见面"**，只比整体语义。
rerank 把 `[query + document]` 拼在一起送模型，能看到词级交互，排序准得多。

实测对比（同一个问题）：

```
融合+文本 (RRF)                          融合+文本 +rerank
  1. 0.0328  1. 手工焊接                  1. 0.9033  （5） 焊接的步骤   ← 提到首位
  2. 0.0320  3. 3. 4 焊接要领              2. 0.8550  1. 手工浸焊
```

代价是无法预计算，只能对少量候选跑（本平台对 20 条候选重排）。

## 分块策略

### 两级结构

```
父块 = 最小一级小节        例：3.3 手工焊接工艺 > 3. 3. 4 焊接要领
子块 = 段落/列表项/表格    例：一条要领
```

- 命中子块 → 返回父块（整节上下文）
- 子块正文前缀 = `【章节路径】`，自带上下文

### 章节树不依赖标题约定

PDF 只是实例，不同文档标题风格差异很大。所以三级降级：

```
① 编号推导    1.4 → 1.4.1 判定更深；1.3.2 下出现 "1." 判定为子项
     ↓ 不适用
② 解析器 level  用 MinerU 给的 level 字段
     ↓ 不适用
③ 单级兜底    所有标题视为同级，只保留"最近标题"作上下文
```

**无标题文档**自动切滑动分组，path 为空，完整上下文由父块提供。

### 踩过的坑：列表项被当成标题

MinerU 会把 `1. 安全措施` / `2. 安全操作` 这类**列表项也标成 title**。
若对单段编号直接取段数，`2. 安全操作` 会被判成 1 级并**清空整个标题栈**，
污染后续所有路径。

规则：**单段编号 = 列表项 → 与上一个标题同级**，且不允许顶掉文档级根标题。
修复后路径异常率 1.5%（5/336）。

## 关键实现细节

### 确定性 id

chunk id 用 `uuid5(doc_id + 章节路径 + 顺序 + 内容哈希)`，**不是随机 uuid4**。

原因：随机 id 会让"同一文档重跑入库"产生**重复点**而不是覆盖更新
（实测踩过：431 个 chunk 变成 862 个点）。内容寻址后重跑天然幂等。

### 缓存

| 缓存 | 位置 | 作用 |
| --- | --- | --- |
| 图片描述 | `data/work/image_desc_cache.json` | 按图片内容哈希，重跑不重复调 VLM |
| 向量 | `data/work/embed_cache.json` | 按内容哈希，重跑**零 API 调用** |

实测重跑：431 → 431 个点，缓存命中 1018、新算 0。

### 图片与表格的处理

- 图片输出 **Markdown 语法** `![图注](URL)`，不用 `<img>`
  （Open WebUI 只渲染前者）
- 表格同时保留 **HTML**（能渲染 HTML 的前端更好看）和**截图**（兜底）
- 图注被标题隔开时，把图**移到图注旁边**，保证图与图注同块

## 目录结构

```
multimodal_kb/           ★ 核心包（零第三方依赖）
├── config.py            所有可调项，一律走环境变量
├── models.py            领域模型（完整保留 bbox/章节树/图片对象）
├── pipeline.py          编排：解析→分块→标注→向量化→入库
├── parse/mineru.py      MinerU 官方 API + 本地 CLI
├── chunk/structure.py   结构重建 + 两级分块
├── annotate/vlm.py      图片语义标注
├── embed/dashscope.py   三路向量 + rerank
├── store/qdrant_store.py Qdrant（原生 HTTP，无第三方依赖）
├── search/hybrid.py     混合检索 + RRF
├── service/app.py       HTTP 服务（stdlib http.server）
└── cli/main.py          kb 命令行

integrations/            第三方适配（与核心解耦）
deploy/                  部署
scripts/                 运维脚本
tests/                   测试 + 题集
docs/                    文档
experiments/             研究实验留档
```
